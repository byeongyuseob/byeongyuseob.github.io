## 요약

2016년부터 서버 6만 대+ 규모 데이터센터에서 서버 하드웨어를 입고부터 폐기까지 운영했습니다. 처음에는 손으로 하던 업무를 팀 최초의 웹 솔루션으로 옮기고 설치를 표준화했고, 이후 원인을 알 수 없던 성능 저하를 분석하고, 수천 대 단위의 일괄 설정 변경을 현장에서 받쳤습니다. 검수 자동화와 장애 대응 표준화는 [대규모 서버 운영 자동화](/work/ops-automation/)에 따로 정리했습니다.

## 업무 시스템화의 시작 (2016 – 2018)

입사했을 때 팀에는 업무용 웹 솔루션이 없었습니다. 신입 시절이라 큰 프로젝트를 맡기보다는 맡은 운영 업무를 하면서, 손으로 하던 일을 하나씩 시스템으로 옮겼습니다. 팀에서 처음 만든 웹 솔루션이었습니다.

### 서버 이전 작업 정보

서버를 다른 랙이나 센터로 옮길 때 대상, 위치, 일정을 손으로 적고 있었습니다. 이 정보를 웹 솔루션으로 옮기고 API로 처리하게 했습니다.

### 종이 일지 3종의 웹화

업무일지, 인수인계 일지, 인프라 점검일지를 종이에서 웹으로 옮겼습니다. 이 세 일지는 10년 뒤인 2026년에 다시 맡아, 하나의 [근무일지로 통합](/work/idc-ops-digital/)하고 있습니다.

### 설치 표준화

- 서버를 입고부터 폐기까지 관리했습니다.
- Kickstart와 profile 이미지로 설치 환경을 표준화하고 OS 설치를 자동화해, 설치에 드는 시간과 사람이 하던 실수를 줄였습니다.

| 만든 것 | 이전 | 이후 | 기술 |
|---|---|---|---|
| 서버 이전 작업 정보 | 손으로 작성, 서버당 최소 5분 | 웹 + API, 서버당 3초 이내 | Python, MongoDB |
| 업무·인수인계·점검 일지 | 종이 | 웹 | Python, MongoDB |
| OS 설치 | 수동 설치 | Kickstart · profile 이미지 자동 설치 | Kickstart |

## 성능 문제와 일괄 변경 (2020 – 2021)

### 메모리 성능 저하 (2020.04 – 07)

| 가설 | 확인한 방법 | 결과 |
|---|---|---|
| 부품 불량·호환성 | CPU, 메모리, 시스템 보드를 새 부품으로 교체 후 Intel MLC로 측정 | 같은 증상, 하드웨어 고장 아님 |
| CPU와 메모리 사이 동작 | 메모리 구성을 최소로 줄여 가며 실험 | CPU P-state와 관련된 것으로 좁힘 |
| 설정 | UEFI 설정 초기화 후 IDC 환경에 맞게 재조정 | 완전히 해결되지 않음 |
| firmware | UEFI, BMC(IMM) firmware 최신화와 로그 분석, 제조사 글로벌 기술지원 협업 | UEFI v2.31로 해결 |

1. CPU, 메모리, 시스템 보드를 새 부품으로 교체하고 Intel MLC로 메모리 성능을 다시 쟀습니다.
2. 메모리 구성을 최소로 줄여 가며 CPU와 메모리 사이의 영향을 확인했습니다.
3. UEFI 설정을 초기화하고 IDC 환경에 맞게 다시 맞췄습니다.
4. UEFI와 BMC(IMM) firmware를 최신으로 올리고, 영향받은 서버 로그를 분석해 다른 서버에 미칠 영향도 확인했습니다.
5. 제조사 글로벌 기술지원팀과 자료를 주고받으며 원인을 좁혔고, UEFI v2.31로 해결했습니다.
6. 증상이 없던 서버에도 BMC firmware를 미리 올려 잠재적인 장애를 막았습니다.

## 쓴 도구

| 도구 | 용도 |
|---|---|
| Kickstart · profile 이미지 | OS 설치 환경 표준화와 자동 설치 |
| Intel MLC (Memory Latency Checker) | 부품 교체 전후 메모리 성능 비교 |
| BMC(IMM) 로그 | 하드웨어 이벤트 확인과 제조사 분석 자료 |
| 관리 proxy · OOB 설정 | 팬 최소 속도를 서버를 끄지 않고 대량으로 변경 |
| UEFI·BIOS 설정 | UEFI 설정 초기화와 재조정 |
| firmware 버전 목록 | 같은 모델·조합 서버를 골라 선제 적용 |

## 정리

- 하드웨어 운영은 한 대를 고치는 일보다 같은 모델, 같은 firmware 조합을 가진 수천 대를 같은 기준으로 다루는 일이었습니다. 설치 표준화, 검수 자동화, 일괄 변경이 모두 그 기준을 맞추는 작업이었습니다.
- 두 건 모두 처음에는 하드웨어 고장이나 냉각 부족처럼 보였지만 원인은 firmware와 센서에 있었습니다. 이후로는 부품 교체 전에 firmware 버전, 센서 값, 전력·냉각 설정부터 확인합니다.
- 대량 변경은 사전 테스트로 부작용(전력)을 먼저 확인하고, 작업 단위를 나누고, 현장 모니터링을 붙이는 순서로 진행됐습니다.
- 증상이 난 서버만 고치지 않고, 같은 모델 전체에 조치를 적용했습니다.

## GPU 노드에 옮기면

GPU 노드도 같은 lifecycle을 거칩니다. 입고 검수, firmware 관리, 성능 저하 분석, 일괄 변경이 그대로 이어지고, 확인할 도구만 바뀝니다.

| 서버에서 한 것 | GPU 노드에서 할 것 |
|---|---|
| 입고 후 설치 표준화 · 검수 | 입고 후 burn-in과 `dcgmi diag`, `nccl-tests`로 노드와 통신 검수 |
| 센서와 팬 | GPU 온도와 throttle 사유(`nvidia-smi -q -d TEMPERATURE,PERFORMANCE`), 랙·노드 온도 비교 |
