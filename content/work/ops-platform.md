| 관측 | `healthz`, `livez`, `readyz`, `metrics`(Prometheus), OpenAPI 문서 |

### 상태 감시

- Worker는 약 1초마다 heartbeat를 남깁니다. 콘솔은 15초 이내면 정상, 30초 이내면 지연, 그 뒤는 중단으로 표시합니다.
- 별도 watchdog이 heartbeat가 60초 넘게 끊기거나 대기열이 5분 넘게 밀리면 관리자 전원에게 한 번 알리고, 정상이 2번 연속 확인되면 복구 알림을 보냅니다.

### 설계에서 내린 판단

| 판단 | 대안 | 고른 이유 |
|---|---|---|
| 등록은 하나로, 실행은 채널별로 분리 | 완전 통합, 또는 채널마다 별도 키 | 채널마다 트래픽 성격이 달라 한쪽이 몰리면 다른 쪽이 막힐 수 있습니다. 채널마다 키를 따로 주면 사용하는 쪽 부담이 커집니다. |
| 메일은 같은 큐와 상태를 쓰고 Worker 프로세스만 분리 | 별도 테이블, 또는 같은 Worker 안에서 분기 | 콘솔, 감사, 백업이 한 테이블 위에 있어 큐는 나누지 않았습니다. 대신 메신저 키가 막혀도 메일 발송은 멈추지 않게 프로세스를 나눴습니다. |
| 중복 방지 키를 알림 테이블 컬럼에 저장 | 별도 테이블 | 기존 30일 정리 작업이 키도 함께 지웁니다. 키를 쓰면 접수는 정확히 한 번, 전달은 at-least-once가 됩니다. |
| at-least-once | at-most-once | 알림이 빠지는 것보다 드물게 두 번 가는 쪽이 낫다고 판단했고, 그 점을 문서에 적었습니다. |
| 승인 없이 셀프서비스 등록 | 관리자 승인, 채널 허용 목록 | 등록하면 바로 쓰게 하고, 대신 하루 한도와 감사 기록으로 관리합니다. |
| 같은 디스크 복제본은 두지 않음 | 로컬 백업 사본 추가 | 같은 디스크에 하나 더 두는 것은 복구력을 높이지 않습니다. |

### 운영

- 배포는 명령 하나입니다. 빌드, 이전 실행 종료, 백업, 추가만 하는 DB 변경, 재시작, 90초 안 상태 확인 순서로 진행합니다.
- 실패해도 자동으로 되돌리지 않고 복원 스크립트로 되돌립니다. 중간에 끊겨도 같은 명령을 다시 실행하면 이어서 진행합니다.
- 백업은 하루 1번 SQLite 온라인 백업과 SHA-256 목록을 만들고 7일 보관합니다. 마지막 성공이 36시간을 넘으면 경고합니다.
- 배포 전 확인은 세 단계입니다. 전체 테스트, 부하 확인(100건 접수에 중복·유실 0건, 101번째 요청 429, 5분 안에 대기열 해소), 화면 확인(360/768/1024/1440px)입니다.
- 사용 서비스는 2개, 5개, 10개, 최대 20개 순서로 늘려 가는 계획을 세웠습니다.
- 장애 시나리오 11종(401, 403, 429, 5xx, timeout, SIGTERM 30초 등)을 정의했습니다.

### 남은 과제

- 단일 SQLite와 단일 Worker 구조는 규모가 커지면 병목이 됩니다.
- 채널별 한도가 없어 한 서비스가 몰리면 다른 서비스에 영향을 줄 수 있습니다.
- 서비스를 멈춰도 담당팀에 자동으로 알리지 않습니다.

### 설계에서 내린 판단

- 실행은 LLM이 아니라 규칙이 합니다. LLM은 의도만 뽑고, 출력이 이상하면 아무것도 호출하지 않습니다(fail closed).
- 처음에는 예비 모델을 두지 않았습니다(동작 예측성). 이후 재시도할 수 있는 전송 오류일 때만 예비 모델로 넘기고, 형식 오류는 같은 모델에 한 번 고쳐 달라고 요청하도록 바꿨습니다.
- 여러 도구를 묶은 복합 도구는 반복되는 질문이 확인된 뒤에만 만들기로 했습니다.
- 캐시 저장소(Redis)가 죽으면 캐시는 건너뛰고, 요청 수용은 막습니다. 제어되지 않은 트래픽보다 제한된 부하가 낫다고 봤습니다.
- 답변 품질은 LLM 판정 대신 계약 기반 평가기로 봅니다.

### 검증

- 테스트 파일 80개, 테스트 676개, 자연어 질문 1,118개, 답변 품질 시나리오 489개로 검증했습니다.
- 사내 베타 API의 자산 64개로 실제 호출을 확인했습니다.
- 아직 HTTP 전송, 메신저 Bot 연동, 사용자 권한은 붙이지 않았고 운영 배포는 하지 않았습니다.

### 설계에서 내린 판단

- 컨테이너 하나가 멈춰도 전체 수집이 막히지 않게 명령마다 120초 제한을 두고, 결과가 비면 해결이 아니라 점검 못 함으로 처리합니다.
- 소스가 절반 넘게 사라지면 코드 점검 결과를 해결로 보지 않고 이전 결과를 이어 씁니다. 잘못된 해결 표시를 막기 위해서입니다.
- 대시보드 이미지는 Alpine 대신 Debian으로 정했습니다. 서버의 docker 20.10 seccomp가 Alpine musl의 syscall을 막았기 때문입니다.
- K3s로 넓힐 때는 컨테이너 목록 함수만 kubectl로 바꾸면 되게 나눠 두었습니다.

## 정리

- 세 도구 모두 사람이 기억하거나 하나씩 확인하던 것을 한 곳으로 모았습니다. 키는 게이트웨이 한 곳, 조회는 MCP 도구 계층 한 곳, 점검은 대시보드 한 곳입니다.
- LLM을 쓰는 부분은 LLM이 할 일을 좁혔습니다. MCP 서버는 의도 해석만, 점검 도구는 한 줄 요약만 맡기고, 실행과 판정은 규칙이 합니다.
- 실패했을 때의 동작을 먼저 정했습니다. 알림은 빠지지 않게, 조회는 이상하면 멈추게, 점검은 모르면 모른다고 표시하게 했습니다.
