## 2017 — 서버 정보 수집 자동화

- 모든 서버 작업을 기록 · 추적하는 ticket 기반 관리 시스템을 만들고 CMDB 와 연동
- dmidecode, MegaRAID 등 제조사 · 모델별 수집 도구를 모듈화해 명령 하나로 통합
- Ansible Playbook 으로 서버 정보를 자동 수집해 중앙 DB 에 저장, 보고서로 변환
- 결과: 대당 수 분씩 걸리던 수작업 검수가 자동화되고, 입고 · 설치 · 변경 작업에서 **전 서버 전수 검수**

## 2019 — 장애 대응 표준 프로세스

- 과거 장애 기록과 로그를 분석해 반복 패턴을 찾고, 보안 · compliance 기준에 맞는 표준 대응과 **안전한 명령어 세트**를 정의
- 장애 유형별 매뉴얼을 만들고 교육 · 훈련 운영
- 결과: 누가 맡아도 같은 절차로 대응하게 되면서 처리 시간과 잘못된 명령으로 인한 2차 장애가 줄었다.

## 2021 – 22 — 장애 관리 웹 인터페이스

- 배경: 서버 60,000대 이상에서 하드웨어 · OS 장애가 **하루 30~40건**. 여러 사람이 서버에 직접 접속해 보안 위험과 처리 지연이 생겼다.
- SSO 와 proxy 로 접근을 중앙화하고, Ansible Dynamic Inventory 로 서버 정보를 실시간 관리
- 하드웨어 · OS 장애를 유형으로 나누고 유형별 Ansible Playbook 작성
- Flask · Vue.js 웹 콘솔, Elasticsearch · Kibana 로 장애 추세 시각화
- 결과: 서버에 직접 접속할 일이 거의 사라졌고, 정형 장애는 Playbook 실행 한 번으로 분 단위에서 수십 초 수준으로 처리. 경험이 적은 엔지니어도 같은 절차로 처리한다.

## 배운 것

- 자동화는 한 번에 오지 않았다. **표준 절차가 먼저 있어야 Playbook 으로 옮길 수 있고, Playbook 이 있어야 웹으로 열 수 있다.**
- 이 구조는 GPU 노드의 health check → 자동 drain → 조치 흐름과 같다.
