## 요약

서버 하드웨어 장애가 나면 현장에서는 티켓 확인, OOB로 하드웨어 상태와 로그 확인, 벤더 점검 요청 메일, 서버 셧다운, 예비 부품 확인을 해야 합니다. 이 일을 한 화면에서 처리하는 장애 처리 웹을 여러 명이 함께 만들었고, 저는 PM으로 기능 대부분을 기획하고 운영했습니다. 2026.08부터 10월까지 기능 추가와 수정을 업데이트 공지 16건으로 내보냈습니다.

## 하드웨어 상태를 언제 수집할지

처음에는 티켓이 생길 때와 티켓 상태가 바뀔 때 자동으로 수집했습니다. 그런데 점검하면서 OOB 케이블이나 전원 케이블을 빼면 수집이 안 되고, 화면에는 예전에 수집한 값이 남아 있었습니다. 실제 서버는 꺼져 있는데 상태 요약은 켜져 있다고 나오는 불일치가 생겼습니다.

## 설계에서 내린 판단

| 판단 | 근거 |
|---|---|
| 신규 티켓 자동 점검은 등록 3분 뒤에 | 바로 돌리면 ping fail 케이스를 놓칩니다. 워런티 안 장비만 대상으로 했습니다. |
| 셧다운 버튼은 30분 안에 서비스 체크를 했고 서비스가 빠진 서버에서만 활성화 | 서비스가 아직 붙어 있는 서버를 끄지 않기 위해서입니다. 셧다운 자체는 기존 운영 도구의 API를 그대로 씁니다. |
| 셧다운 요청 5분 뒤 실행, 진행 중에는 ping 표시를 노란색으로 점멸, 최대 10분까지 꺼짐 확인 | 서버가 꺼지는 중에도 ping이 응답하는 경우가 있어서, 바로 실패로 보지 않고 실제로 꺼진 시각까지 확인합니다. |
| 점검 요청 묶어 보내기는 워런티 안, 같은 벤더, 같은 IDC일 때만 | 묶어도 발송 조건(서비스 체크, 요청 내용)은 티켓마다 똑같이 검사하고, 로그도 티켓마다 수집 가능한 종류만 붙입니다. |
| 로컬 파일 업로드 추가 | 클라우드 망에 있는 GPU 장비처럼 시스템이 로그를 직접 가져올 수 없는 장비가 있었습니다. 따로 뽑은 로그를 올리면 드라이브에 올리고 링크로 메일에 붙입니다. |
| 예비 부품 조회에서 메모리·디스크는 예비 수량, CPU·GPU는 같은 스펙 예비 장비 목록, NIC는 제외 | 부품 관리 API가 메모리·디스크만 지원하고, NIC는 장비 정보에 대표 NIC만 나와서 맞는 값을 줄 수 없었습니다. |
| 통합 뷰에서 클라우드 장비의 작업 버튼은 비활성 | 두 조직의 점검 절차가 아직 하나로 정리되지 않아, 목록만 먼저 열고 작업은 절차가 정리된 뒤 열기로 했습니다. |

## 정리

- 기능은 현장에서 실제로 막힌 곳에서 나왔습니다. 꺼진 서버가 켜진 것으로 보인 일이 수집 시점을 바꿨고, 로그를 못 가져오는 GPU 장비가 로컬 업로드를 만들었습니다.
- 서버를 끄는 기능은 막는 조건부터 정했습니다. 서비스 체크 이력과 서비스 제외 상태가 없으면 버튼이 열리지 않습니다.
- 데이터가 없는 부품(NIC)은 억지로 보여 주지 않고 지원하지 않는다고 밝혔습니다.
