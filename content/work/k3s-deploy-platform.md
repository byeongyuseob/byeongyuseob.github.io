## 요약

사내 IDC 개발 서버는 서버에 직접 세팅하던 방식을 거쳐 Docker 컨테이너로 운영되고 있었습니다. 운영 서버와 개발 서버의 구분이 모호했고, 관리 도구는 로그인 문제가 있었고, 관리자 권한은 여섯 곳에 흩어져 있었습니다. 2026년 6월 4명으로 TF를 꾸렸고, 저는 PM으로 설계부터 구축까지 참여했습니다. 8월부터 K3s 클러스터를 세웠고, 10월에는 개발자가 이슈 양식만으로 앱을 만들고 운영에 반영하는 배포 체계가 돌고 있습니다.

## TF 구성과 맡은 일

| 영역 | 담당 |
|---|---|
| PM, 설계 방향과 일정 | 저 |
| 배포 파이프라인, 네트워크 | 저와 동료 1명 |
| 스토리지 | 동료 1명 |
| 모니터링 | 동료 1명 |

구현은 파이프라인을 함께 맡은 동료와 같이 했고, 위키 문서는 그 동료가 정리했습니다. 9월에는 배포 가이드를 처음 보는 사람처럼 따라가며 전체 배포 테스트를 하고 결과를 점검했고, 9월 말 TF 발표에서는 배포 파이프라인 부분을 맡았습니다.

## 구조

| 층 | 구성 | 정한 이유 |
|---|---|---|
| 진입점 | 사내 L4 LB, 경로 기반 도메인 하나 | 클러스터가 고장 나도 진입점에서 진단할 수 있게 클러스터 밖에 두었습니다. 앱마다 도메인, 인증서, SSO를 따로 신청하지 않도록 도메인 하나를 경로로 나눴습니다. |
| 인증 | 사내 SSO와 연동한 인증 서비스, Redis 세션 | 사내 SSO는 반복 호출을 막기 때문에 로그인 1회에 2번만 부르고, 이후 요청은 세션만 봅니다. 앱에는 인증 코드가 없고 신원 헤더만 읽습니다. |
| 라우팅 | Traefik, 경로 라우터 2대 | 진입에서 위조된 신원 헤더를 지웁니다. 라우터는 두 노드에 나눠 두고 페일오버를 10번 시험해 10번 모두 넘어가는 것을 확인했습니다. |
| 클러스터 | K3s, 내장 etcd, Cilium | 아래 판단 참고. 지금은 컨트롤 플레인 1대와 워커 1대이고, 마스터 3대와 워커 2대로 늘리는 계획은 장비를 기다리고 있습니다. |
| 빌드와 배포 | GitHub Actions(클러스터 안 ARC 러너) + BuildKit, Harbor, ArgoCD ApplicationSet | 공용 러너에는 Docker가 없어 클러스터 안에 러너를 띄웠고, 빌드 데몬을 상주시켜 캐시를 유지했습니다. |
| 저장소 | Longhorn(앱 볼륨), MinIO(백업과 이미지 저장) | MinIO는 Longhorn 위에 두지 않아 복원이 서로를 기다리지 않게 했습니다. |
| 관리 도구 | Rancher, ArgoCD, Harbor를 dex로 사내 SSO에 연결 | 관리자 명단은 파일 하나에서 생성하고, 머지 뒤 최대 3분 안에 각 도구에 반영됩니다. |

## TF에서 내린 판단

| 판단 | 이유 | 결과와 대가 |
|---|---|---|
| 데이터스토어를 SQLite에서 내장 etcd로 전환 | 마스터를 3대로 늘리려면 SQLite로는 조인할 수 없고, 외부 DB를 두면 그 DB가 새 단일 장애점이 됩니다. | 전환 전후 리소스를 비교해 바뀐 것은 노드 역할 1줄뿐이었고, 서비스는 멈추지 않았습니다. |
| 클러스터 API는 진입 LB에 넣지 않음 | 워커가 k3s 내장 로컬 LB로 마스터에 붙는 것을 워커에서 직접 확인했습니다. | 진입 LB는 서비스 트래픽만 받습니다. |
| CNI를 재설치 없이 flannel에서 Cilium으로 교체 | 출발지 IP 고정과 노드당 파드 수 목표가 있었습니다. Cilium의 cluster-pool IPAM은 기존 podCIDR를 읽지 않아 대역 확장이 교체와 함께 따라옵니다. | 작업 창 약 1시간, 데이터 손실 0, 노드당 파드 주소 254 → 2,046개, 클러스터 파드 한도 220 → 1,210개. 전환 전 값을 설정에 고정해 두는 바람에 두 노드가 25분 동안 NotReady였습니다. |
| 레지스트리를 zot에서 Harbor로 교체 | 운영을 넘겨받을 사람이 참고할 사내 자료가 Harbor 쪽에 훨씬 많았습니다. | 이미지는 다이제스트를 대조하며 옮겼고, 보존정책과 GC를 켰습니다. |
| 비밀값은 Sealed Secrets, 키 회전은 끔 | ArgoCD를 고치지 않고 나중에 되돌릴 수 있는 방식입니다. 백업 없이 키를 회전하는 것보다 회전 없이 백업하는 쪽을 택했습니다. | 기존 Secret 10개의 해시가 그대로였고 파드 재시작은 없었습니다. 유출 시 위험은 감수한다고 기록했습니다. |
| 승인은 운영 되돌리기와 운영 삭제에만 | 거의 항상 통과하는 승인은 배포만 늦춘다고 판단했습니다. | 나머지는 빌드 전 계약 검사와 배포 뒤 자동 확인이 맡습니다. |
| 배포 뒤 확인이 판정할 수 없으면 되돌리지 않음 | 판정할 수 없는 상태를 실패로 읽어 멀쩡한 배포를 되돌린 일이 있었습니다. | 10월 27일까지 운영에서 자동 되돌림이 실제로 3번 동작했습니다. |

## 숫자로 본 결과

| 러너 대기 | 13분 40초 | 11~24초(러너 5대 → 최대 10대, 배포 전용 풀) |
| ArgoCD 동기화 시작 | 2분 37초(폴링) | 약 2초(웹훅) |

배포 뒤 확인과 자동 되돌림을 넣기 전에는 3~5분이었습니다. 확인 단계를 넣으면서 늘어난 시간을 러너와 동기화 대기를 줄여 되찾았습니다. 10월 27일 기준 ArgoCD 앱 29개가 모두 Synced, Healthy였고 최근 배포 100건이 모두 성공했습니다.

## 겪은 장애와 바꾼 것

- 8월 대역 이관 재구축 중에 볼륨을 옮기는 단계가 실행되지 않은 채 제거 단계가 돌아, 볼륨 디렉터리가 사라졌습니다. 미리 받아 둔 DB 덤프로 3개 DB를 모두 복구했습니다(일부 실행 이력은 잃었습니다). 이후 위험한 단계 사이에 사람의 확인 대신 기계적인 확인 게이트를 넣었습니다.
- 인증서 감시가 만료일만 보고 있어서, 우리 인증서가 빠진 상태를 기본 인증서의 남은 기간으로 정상이라고 읽었습니다. 인증서가 누구의 것인지부터 검사하도록 고쳤습니다.
- 관리 도구 권한을 회수하는 길이 한 번도 작동하지 않는 구조였습니다. 권한 명단을 별도 자동 동기화로 떼어 내 회수도 머지 한 번으로 되게 했습니다.
- 브랜치 보호를 건 뒤 경로 자동화의 직접 push가 막혀 셀프서비스가 약 10시간 멈췄습니다. 보호를 걸기 전에 main에 직접 push하는 주체부터 세어야 했습니다.
- CI 이미지 push가 나흘 동안 막혔습니다. 같은 파드에서 경우를 셋으로 나눠 시험해, 토큰을 받아오는 쪽이 빌드 데몬이 아니라 클라이언트라는 것을 확인하고 고쳤습니다.

## 남은 과제

- 워커 2대와 마스터 2대 증설은 장비를 기다리고 있습니다. 지금은 워커 1대가 죽으면 서비스가 모두 멈춥니다.
- 백업이 같은 디스크 안에 있습니다. 클러스터 밖으로 나가는 백업은 아직 없습니다.
- 배포기와 인증 서비스가 아직 한 대씩입니다.

## 알게 된 점

- 가장 많이 나온 장애 유형은 "초록인데 실제로는 깨진" 경우였습니다. 2xx 응답이나 통과 표시 대신 파일 내용, 렌더 결과, 해시 같은 실제 결과로 판정하게 바꿨습니다.
- 승인 단계를 늘리는 것보다 빌드 전에 검사하고 배포 뒤에 확인하는 쪽이 개발자의 속도와 안전을 함께 지켰습니다.
- 문서에 위험을 적어 두는 것만으로는 실행 중의 실수를 막지 못했습니다. 되돌리기 어려운 단계 앞에는 기계적인 게이트를 두었습니다.
