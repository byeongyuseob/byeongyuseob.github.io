## 요약

사내 서비스마다 언어와 배포 방식이 달라 관리가 어려웠고, 사람이 직접 배포하다 생긴 서비스 중단과 오류가 1년에 10회 이상 있었습니다. PM으로 개발 스택과 코드 규칙을 먼저 표준화하고, 환경별 Docker 이미지와 GitHub Actions 파이프라인으로 배포를 하나로 정리한 뒤, 모니터링과 메신저 배포 채널 알림을 붙였습니다.

## 배경

| 문제 | 영향 |
|---|---|
| 서비스마다 다른 언어와 배포 방식 | 업데이트와 관리가 어렵고, 새 서비스를 추가하거나 늘리기 어려움 |
| 사람이 직접 하는 배포 | 배포에 평균 60분, 배포 실수로 서비스 중단과 오류가 1년에 10회 이상 |
| 문제를 늦게 알아챔 | 알아채고 원인을 찾아 해결하는 데 평균 2시간 |

DevOps 원칙에 맞는 배포 시스템이 필요하다고 보고 프로젝트를 시작했습니다.

## 목표

- 언어와 기술 스택을 표준화해 유지보수와 관리 부담을 줄이기
- 컨테이너 기반 환경으로 배포 환경을 안정적으로 만들기
- CI/CD 자동화와 표준화로 배포 과정을 안정화하기
- 서비스가 늘어나도 같은 방식으로 추가할 수 있는 구조 만들기

## 설계에서 내린 판단

| 판단 | 근거 |
|---|---|
| 자동화보다 스택 표준화를 먼저 | 서비스마다 언어와 배포 방식이 달라 업데이트·관리·서비스 추가가 어려웠던 것이 출발점이었습니다. |
| 환경별 컨테이너 이미지로 배포 단위 통일 | 표준 스택마다 환경에 맞는 이미지를 만들어 이미지 빌드 과정을 자동화하고 표준화했습니다. |
| Alpine 기반 이미지와 빌드 캐시 | 배포가 지나치게 오래 걸리던 원인을 찾아 보니 빌드 과정이어서, 빌드와 캐시 전략을 고쳤습니다. |
| 알림을 메신저 배포 채널 하나로 | 문제가 생겼을 때 팀이 같은 채널에서 바로 확인하고 대응하게 하려는 목적이었습니다. |

## 결과

- push하면 빌드와 테스트를 거쳐 자동으로 배포되도록 바꿨습니다.
- 배포 절차가 하나로 정리되면서 배포 실수로 인한 장애가 줄었습니다.
- 빌드 과정과 캐시 전략을 고쳐 배포 시간을 평균 60분에서 30분으로 줄였습니다.
- 실시간 모니터링과 메신저 배포 채널 알림으로 문제 해결 시간을 평균 2시간에서 30분으로 줄였습니다.

과정과 결과는 기록 글 [사내 배포를 하나의 파이프라인으로 정리하기](/posts/deploy-pipeline/)에도 정리했습니다.
