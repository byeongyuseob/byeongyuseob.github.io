## 요약

서버 하드웨어 장애 한 건을 처리하려면 티켓 화면, 자산 정보 화면, 장애 처리 웹을 오가야 했습니다. 크롬 확장과 작은 백엔드를 만들어, 엔지니어가 이미 보고 있는 티켓 화면 안에 서버 정보, 하드웨어 상태, 조치 버튼을 붙였습니다.

- 데이터는 화면 스크래핑 대신 각 시스템의 API로 가져옵니다. 티켓 화면에서 읽는 것은 주소의 티켓 번호와 섹션을 붙일 위치 하나뿐입니다.
- 자격 증명은 "누구 권한으로 실행돼야 하는가"로 나눴습니다. 공용 API 키와 토큰은 백엔드에만 두고, 실행자 기록이 남아야 하는 조치는 사용자 본인 로그인 세션으로 부릅니다. 확장 안에는 비밀값이 없습니다.
- 숙련자의 처리 시간은 크게 줄지 않을 수 있어서, 효과는 기대 효과로만 적고 잴 방법을 먼저 정했습니다.

## 장애 한 건에 화면 세 개

장애 티켓이 들어오면 처리하는 사람은 대략 이런 순서로 화면을 옮겨 다녔습니다.

| 확인할 것 | 있던 곳 |
|---|---|
| 증상, 대상 호스트, 접수 내용 | 티켓 화면 |
| 위치(랙), 담당자, 운영 구분, 벤더, 워런티, 부품 구성 | 자산 관리(CMDB) 화면 |
| 같은 스펙 예비 부품 수량 | 부품 재고 화면 |
| 전원·부품 상태, BMC 로그, 서비스 체크, 로그 수집, 벤더 점검 요청 메일 | 장애 처리 웹 |
| 교대 인계, 공유 | 메신저에 직접 정리 |

화면 하나하나는 문제가 없었습니다. 문제는 화면 사이를 잇는 일이 사람 몫이라는 점이었습니다. 티켓에서 자산번호를 복사해 자산 화면 검색창에 붙이고, 호스트명을 다시 복사해 장애 처리 웹에서 찾습니다. 도구가 늘어날수록(tool sprawl) 사람이 시스템 사이에서 값을 옮겨 나르는 다리가 됩니다. 의자를 돌려 가며 이 화면의 값을 저 화면에 옮겨 치던 모습에서 swivel-chair 문제라고도 부릅니다.

## 사람의 context switching 비용

CPU도 context switching에 비용을 냅니다. 레지스터를 저장하고 복원하는 직접 비용은 작고, 비싼 것은 전환한 뒤입니다. 새 작업이 캐시를 자기 데이터로 채우면서 앞 작업의 데이터가 밀려나고(cache pollution), 주소 공간이 바뀌면 TLB를 다시 채워야 하고, 진행 중이던 파이프라인은 비워집니다. 한 번은 작지만 전환이 잦아지면 실제 일보다 전환에 시간을 더 쓰는 thrashing 상태가 됩니다.

사람도 비슷하다고 봤습니다. 화면을 옮기는 동작은 1초면 끝나지만, 머릿속에 들고 있던 맥락이 흐려집니다. "지금 보는 서버가 티켓의 그 서버가 맞나", "아까 본 워런티가 이 장비 것이었나"를 다시 확인하게 됩니다. 오염된 캐시를 다시 데우는 비용입니다. 장애 판단과 상관없는 "어느 화면에서 무엇을 찾나"가 cognitive load를 차지합니다.

평소에는 이 비용이 작습니다. 하지만 장애가 몰리거나 급하게 처리해야 할 때는 이 틈에서 다른 서버에 조치하거나 다른 티켓의 장비로 벤더에 요청하는 실수가 생길 수 있고, 조치 실수는 또 다른 장애로 이어질 수 있습니다.

## 티켓 화면을 작업 자리로

도구를 하나 더 만드는 대신, 엔지니어가 이미 머무는 티켓 화면에 필요한 것을 붙였습니다(in-context integration). 티켓 팝업을 열면 확장이 '기본정보' 위에 섹션을 하나 붙입니다. 티켓 화면과 같은 마크업과 버튼 클래스를 써서 원래 화면의 일부처럼 보이게 했습니다.

## 설계에서 내린 판단

| 판단 | 이유 | 대가 |
|---|---|---|
| 데이터는 화면 스크래핑이 아니라 API로 | 원천 화면이 바뀌어도 데이터는 깨지지 않습니다. 티켓 화면에서 읽는 것은 주소의 티켓 번호와 붙일 위치(요소 하나)뿐입니다. | 붙일 위치와 벤더 메일 창은 여전히 화면에 기대고 있습니다. |
| 공용 키와 토큰은 백엔드에만 | 확장은 사용자 PC에 코드가 그대로 풀려 있어서, 비밀값을 넣으면 그대로 노출됩니다. 키 3개를 서버 env 파일(권한 600)에만 두었습니다. | 키 관리가 서버 한 곳에 몰립니다. |
| 실행자가 남아야 하는 조치는 사용자 본인 세션으로 | 서비스 체크와 로그 수집을 공용 키로 대신 실행하면 누가 했는지가 기록에서 사라집니다. 이 API들은 백엔드용 키도 없었습니다. | 사용자가 장애 처리 웹에 로그인해 있어야 합니다. 확장이 부를 수 있는 경로는 메서드와 경로 패턴 10개로 묶었습니다. |
| 백엔드 권한은 티켓 단위로 | ping은 그 티켓 연관 CI의 IP만 받고, 메신저 받는 사람은 SSO 헤더로만 정합니다. 확장을 고쳐도 아무 IP나 ping하거나 남에게 보낼 수 없습니다. | 다른 장비는 그 장비의 티켓을 열어야 볼 수 있습니다. |
| 가공은 백엔드, 확장은 그리기 | 확장은 웹 스토어 대신 사내 서버에서 압축 파일로 나눠 주어 자동 업데이트가 없습니다. 값 계산을 서버에 두면 확장을 다시 깔지 않고 고칠 수 있습니다. | 화면 모양을 바꾸려면 여전히 새 버전을 깔아야 해서, 패널에 새 버전 알림과 패치 내역을 띄웁니다. |
| 원천 시스템 부하부터 막기 | 하드웨어 상태는 장애 처리 웹이 저장해 둔 결과를 받으면 0.03~0.2초, 장비에서 새로 모으면 약 9초(최대 30초)였습니다. 평소엔 저장된 결과를 받고 '다시 수집'만 새로 모으게 했고, 그것도 티켓마다 1분에 한 번으로 제한했습니다. 무거운 조회는 그 모달을 처음 열 때만 합니다. | 하드웨어 상태가 최대 6시간 전 것일 수 있어서, 몇 시간 전인지 같이 보여 줍니다. 처음에는 이 6시간이 지켜지지 않았습니다(아래 '글을 쓰며 다시 본 것'). |
| 원천이 실패해도 빈 화면은 아니게, 대신 표시는 분명히 | 마지막 성공 결과를 7일 보관해 원천 장애 때 보여 주고, 자산 조회까지 실패하면 티켓의 자산번호와 호스트명만으로 행을 만듭니다. 장애 처리 웹을 운영할 때 지난 값이 남아 꺼진 서버가 켜진 것으로 보인 적이 있어서, 저장된 결과에는 실패 원인과 안내 줄을 붙입니다. | 오래된 값을 최신으로 오해할 여지는 표시로만 막고 있습니다. |

배포 날 운영 환경에서 확인한 숫자도 남깁니다. 하드웨어 상태는 첫 호출 3.97초, 같은 티켓 두 번째 호출은 캐시에서 0.002초였습니다. 컨테이너는 non-root, 읽기 전용 파일시스템으로 띄우고 capability는 ping용 NET_RAW만 남겼습니다. 배포 이미지는 Trivy 취약점 0건으로 올렸습니다.

## 기대 효과

- 인지 부하와 context switching 감소: 같은 장비를 화면마다 다시 찾지 않습니다.
- 조치 과정의 휴먼 에러 가능성 감소: 티켓 제목에 나온 장비를 '대상'으로 맨 위에 두고, 조치 버튼은 그 티켓의 장비만 대상으로 합니다.
- 숙련도에 따른 대응 편차 감소: 숙련자가 머릿속 순서로 하던 확인(연관 CI → 하드웨어 상태 → BMC 로그)이 화면 순서가 됩니다.
- 신규 인력 온보딩 부담 감소: 어느 화면에서 무엇을 찾는지부터 배우지 않아도 됩니다.

MTTR이 크게 줄 거라고는 보지 않습니다. 숙련자는 이미 자기 순서로 빠르게 오가고 있을 것이고, 장애 처리 시간의 대부분은 정보를 모으는 데보다 벤더 점검, 부품 수급, 노드 분리 일정에서 정해집니다. [CPU·GPU 노드 장애 기록](/posts/cpu-gpu-node-fault-comparison/)에서 GPU 교체 한 건이 약 하루 걸린 것도 대부분 그 단계였습니다. 이 확장이 줄이는 것은 그중 앞부분, 사람이 화면을 오가며 맥락을 다시 맞추는 시간입니다.

| 장애 인지 후 첫 조치까지 걸린 시간 | 티켓 접수 시각과 첫 조치(서비스 체크, 로그 수집, 벤더 요청) 기록 시각의 차이. 조치가 본인 이름으로 남아 사람별로도 볼 수 있습니다 |
| 휴먼 에러 건수 | 회고 기록에서 잘못된 서버나 티켓에 조치한 사례 |
| 사용률 | 백엔드 요청 로그의 사용자 수. 티켓 요청마다 누가 어느 티켓을 봤는지 한 줄씩 남깁니다 |
| 사용자 피드백 | 쓰는 사람에게 직접 받습니다 |

같은 사람이 같은 장애를 두 번 처리하면 두 번째가 익숙해서 빨라집니다. 그래서 사람마다 기존 방식과 새 방식의 순서를 바꿔 가며 해 볼 생각입니다.

## 한계와 남은 리스크

- 도구가 오히려 휴먼 에러를 만들 수 있습니다: '대상' 장비는 티켓 제목에 호스트명이 나오는지로 정하고, RAID 상태 점은 원천이 주는 값이 아니라 로그 문구로 추정합니다. 티켓 제목이 틀리면 엉뚱한 장비가 맨 위에 옵니다. 판정 근거는 마우스를 올리면 보이게 해 두었지만, 화면을 믿고 원천에서 다시 확인하지 않는 automation bias는 남습니다.
- 원천 시스템의 권한을 우회합니다: 백엔드는 SSO 로그인만 확인하고 공용 키로 원천을 부릅니다. 원천 시스템에서 볼 권한이 없는 사람도 백엔드를 거치면 볼 수 있는 confused deputy 구조입니다. 원천 시스템이 SSO 사용자 모두에게 열려 있다면 실제 차이는 없지만 아직 확인하지 못했습니다. 지금은 누가 어느 티켓을 봤는지 로그로 남기는 데까지 했고, 원천 권한이 더 좁다면 허용 사용자 목록이 필요합니다.
- 사용자가 늘면 원천 부하도 늘어납니다: 티켓을 한 번 열 때 사용자 세션으로 장애 처리 웹을 약 7번 부르고, 이 호출은 사람 사이에 캐시를 나누지 않습니다. 모두 가벼운 조회이고, 장애 처리 웹 화면도 진행 중인 작업 상태를 2초마다 다시 받는 것에 비하면 작아서 지금은 바꾸지 않았습니다. 부담이 되면 장애 처리 웹에 묶음 조회 API를 두는 것이 맞는 해결입니다.
- API 형식 변경: 조치 기능은 연동 약속이 없는 화면용 내부 API를 써서 예고 없이 바뀔 수 있고, 이를 먼저 알아챌 contract test는 없습니다.
- 인증 토큰 관리: 서비스 키 3개의 교체 절차가 없고, 하나는 다른 시스템과 같이 쓰는 키라 바꾸면 영향이 넓습니다.
- 화면 의존: 섹션을 붙일 위치와 벤더 메일 창은 화면 구조가 바뀌면 깨집니다.
- 자동 업데이트 없음: 옛 버전을 쓰는 사람이 남을 수 있습니다.
- 없는 정보는 못 만듭니다: 장애 처리 웹이 BMC에서 받지 못한 부품 상태는 여기서도 N/A입니다.

## 글을 쓰며 다시 본 것

이 글을 코드와 맞춰 보다가 "화면 값은 최대 6시간 전"이라는 설명이 틀린 것을 찾았습니다. 장애 처리 웹은 6시간 안에 저장해 둔 결과를 주고, 백엔드는 그 결과를 받은 때부터 다시 6시간 보관했습니다. 5시간 된 결과를 받으면 11시간 전 상태가 화면에 '저장된 결과'라고만 나왔습니다. 장애 처리 웹을 운영할 때 겪은, 꺼진 서버가 켜진 것으로 보인 문제와 같은 종류입니다.

| 리스크 | 한 것 | 확인 |
|---|---|---|
| 지난 상태를 최신으로 오해 | 저장 기간을 장비 수집 시각부터 세어 6시간을 넘지 않게 했습니다. 남은 시간이 1분보다 짧으면 1분은 두고, 수집 실패와 함께 온 지난 결과는 화면에 그렇게 표시되므로 6시간 그대로 둡니다. 하드웨어 상태 제목 아래와 OOB Log 줄 머리에 '장비 수집 2시간 전'처럼 보여 주고 1분마다 다시 씁니다. 메신저로 보내는 요약에도 수집 시각을 넣었습니다. | 로컬 fixture로 2시간 전 수집이면 보관 14,386초, 약 25시간 전 수집이면 60초 |

## 정리

- 도구를 하나 더 만드는 대신 사람이 이미 보고 있는 화면에 붙였습니다. 새 도구는 그 자체로 오갈 화면을 하나 더 늘립니다.
- 자격 증명은 "어디에 둘까"보다 "누구 권한으로 실행돼야 하나"로 먼저 나눴습니다. 조회는 공용 키로, 기록이 남아야 하는 조치는 본인 세션으로 합니다.
- 설명을 글로 쓰는 일이 코드 리뷰가 됐습니다. "최대 6시간"이라고 쓰려다 실제로는 12시간 가까이 될 수 있다는 것을 찾았습니다.
- 줄였다고 말하려면 이동 횟수, 첫 조치까지 시간, 휴먼 에러 건수를 먼저 재야 합니다.
