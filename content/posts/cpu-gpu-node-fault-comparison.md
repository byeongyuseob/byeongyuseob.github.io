> 2026.01 – 2026.10 장애 기록, 2026.10.27 분석. 관련 프로젝트: [서버 Fleet 하드웨어 운영](/work/hardware-troubleshooting/)

## 요약

같은 사이트에서 CPU 노드와 GPU 노드를 같이 운영하고 있습니다. 10개월 동안 현장 처리한 서버 장애 티켓 약 14,500건을 두 종류로 나눠 보니, 고장 나는 곳도 처리하는 방식도 달랐습니다.

CPU 노드 장애는 Disk 같은 소모성 부품이 대부분이라 현장 예비 부품으로 당일에 끝나는 일이 많았습니다. GPU 노드 장애는 GPU와 GPU 네트워크에 몰려 있었고, 부품을 바꾸는 시간보다 셧다운 일정을 잡고, 진단하고, 벤더 승인을 받는 시간이 더 길었습니다. GPU 노드에는 CPU 노드에서 볼 수 없는 장애 유형도 따로 있었습니다.

장애가 접수되는 방식도 달랐습니다. CPU 노드 장애는 모니터링 알람이 바로 티켓이 된 건이 68%였는데, GPU 노드 장애는 74%를 담당 SE가 확인하고 노드 분리 일정을 잡은 뒤 직접 접수했습니다.

## 고장 나는 곳이 다르다

| 부위 (HW 장애 중 비율) | CPU 노드 | GPU 노드 |
|---|---|---|
| Disk | 50% | 8% |
| NIC, 광모듈, 케이블 | 16% | 48% |
| GPU | - | 26% |
| Memory | 14% | 3% |
| FAN | 6% | 1% |
| PSU | 4% | 8% |

CPU 노드는 디스크를 많이 꽂는 스토리지용 서버가 많아서 장애의 절반이 Disk였습니다. 교체한 디스크 대부분이 3.5인치 HDD였고, Disk 장애의 96%를 현장 예비 부품으로 바로 바꿨습니다.

GPU 노드는 한 대에 GPU 8장, GPU 사이를 잇는 NVSwitch, 고속 NIC 여러 장과 그만큼의 InfiniBand 광모듈이 들어갑니다. 고장 날 수 있는 큰 부품이 GPU와 GPU 네트워크 쪽에 몰려 있어서 장애도 그쪽에서 났습니다.

## GPU 서버에만 있는 장애

GPU Error로 들어온 485건을 티켓에 적힌 증상으로 나눴습니다.

| 증상 | 건수 | 주로 한 처리 |
|---|---|---|
| GPU 미인식 (Missing, Xid 79, device handle error) | 101 | GPU 교체, 일부는 swap 후 baseboard 교체 |
| ECC, Remapped Row, SRAM error | 27 | GPU 교체 |
| 비정상 온도 | 25 | GPU 교체 |
| PCIe Fatal, Downtrain | 12 | 재장착 또는 swap |
| NVLink, NVSwitch error | 10 | GPU 교체 |
| 그 밖의 Xid | 29 | swap 또는 교체 |
| 증상 상세 기록 없음 | 281 | GPU 교체, swap |

CPU 노드에서는 없는 유형들이고, 운영하면서 느낀 특징은 아래와 같습니다.

- GPU 1장이 문제여도 노드 전체를 내려야 합니다. GPU는 hot swap이 안 되고, 진단도 OS를 끈 상태에서 해야 해서 나머지 7장도 같이 멈춥니다.
- 온도가 교체 근거가 됩니다. GPU 교체 288건 중 73건은 벤더 온도 수집 프로그램으로 온도가 비정상인 GPU를 찾아 바꾼 건이었습니다. CPU 노드 HW 장애 9,265건에는 온도를 근거로 부품을 바꾼 기록이 없었습니다.
- Xid라고 모두 HW 장애는 아닙니다. Xid 94, 137은 벤더가 ECC error 이력이 없음을 확인하고 application 재실행과 GPU reset을 권고해서 교체 없이 종결했습니다. Xid 79처럼 GPU가 bus에서 떨어진 경우는 교체로 이어졌습니다. 같은 GPU Error 알람이라도 Xid 번호를 먼저 봐야 처리 방향이 정해졌습니다.
- 증상이 slot을 따라가는지 봐야 합니다. 의심 GPU를 다른 slot의 GPU와 바꿔 끼워서, 증상이 GPU를 따라가면 GPU 불량, slot에 남으면 baseboard나 PCIe 경로 쪽으로 봤습니다. GPU 교체 건의 34%가 이 swap test를 거쳤습니다.
- InfiniBand 광모듈 장애가 많고 몰려서 납니다. GPU 노드 NIC 장애 691건 중 405건이 한 사이트의 같은 8-GPU 기종에서 나왔고, 그중 78%가 광모듈 교체였습니다. 1월 131건에서 10월 17건으로 줄었는데, 초기 불량이 걸러진 것과 클러스터 용도가 학습에서 추론으로 넘어가면서 노드 사이 InfiniBand 통신이 줄어든 영향으로 보고 있습니다.

## 장애가 접수되는 방식

장애는 두 종류 노드 모두 전사 모니터링 시스템으로 감지됩니다. 차이는 그 다음이었습니다.

| 접수 경로 (고유 건) | CPU 노드 | GPU 노드 |
|---|---|---|
| 모니터링 알람이 바로 티켓으로 | 68% | 25% |
| 담당 SE가 확인 후 접수 | 27% | 74% |
| 그 외 (개발자 등록 등) | 5% | 1% |

CPU 노드는 Disk Error, Ping Fail 같은 알람이 바로 티켓이 되고, 현장에서 부품을 바꾸면 끝났습니다. GPU 노드는 GPU 교체 288건 중 206건, 광모듈 장애 691건 중 650건을 담당 SE가 접수했습니다. GPU 노드는 노드를 서비스에서 빼야 작업할 수 있어서, 담당 SE가 노드 분리 일정을 계획하고 서비스에서 제외한 뒤 현장에 넘기는 흐름이었습니다.

## 같은 알람, 다른 원인

Ping Fail은 두 종류 노드 모두에서 자주 오는 알람인데, 뒤에 있는 원인이 달랐습니다.

- CPU 노드의 Ping Fail은 Memory(707건), CPU(265건), Mainboard(175건) 순서였습니다. BMC 로그에서 Machine Check Exception이나 uncorrectable memory error를 찾는 것으로 시작했습니다.
- GPU 노드의 Ping Fail은 PCIe bus fatal error, DPC error처럼 PCIe switch 아래 GPU나 NIC slot에서 시작된 장애가 서버 다운으로 이어진 경우가 많았습니다. 과열로 system down 된 건도 있었습니다.

같은 알람이 와도 노드 종류에 따라 처음 볼 로그가 달랐습니다.

## 처리 방식이 다르다

| 항목 | CPU 노드 | GPU 노드 |
|---|---|---|
| 벤더 점검을 거친 비율 (HW 장애) | 16% | 58% |
| 현장 예비 부품 사용 기록 (HW 장애) | 65% | 14% |
| F/W 업데이트 동반 (전체 티켓) | 16% | 26% |
| 대표 장애의 처리 시간 중앙값 | Disk 7시간 | 광모듈 1시간, GPU 교체 22.5시간 |

CPU 노드는 현장에 둔 예비 부품으로 운영팀이 판단하고 바로 바꿨습니다. GPU 교체 건은 예비 부품 사용 기록이 3%뿐이었고, 대부분 벤더 엔지니어의 로그 분석으로 교체 승인을 받은 뒤 부품을 받아서 바꿨습니다. 부품이 없어서 다시 방문한 경우가 GPU 교체 건의 14%였습니다.

GPU 교체 1건은 아래 순서로 진행했고, 부품을 바꾸는 시간은 이 중 일부였습니다.

1. 담당 SE가 노드 분리 일정을 계획하고 서비스에서 제외한 뒤 셧다운합니다.
2. AC power cycle 후 BMC 로그와 nvidia-bug-report를 수집합니다.
3. 벤더 온도 수집 프로그램, `dcgmi diag -r 3`, field diagnostic을 돌립니다. 셧다운 일정이 안 잡히면 진단 자체를 못 해서, 12일 동안 보류하다 종결한 건도 있었습니다.
4. swap test로 GPU 불량인지 slot 쪽인지 가립니다.
5. 벤더 승인을 받고 GPU를 교체합니다.
6. BIOS, BMC, GPU baseboard, PCIe switch, CPLD, NIC F/W를 기준 버전으로 맞춥니다. GPU 교체 건의 87%에서 F/W 업데이트를 같이 했습니다.
7. GPU 8장 인식, dcgmi diag 통과, NVLink와 NVSwitch와 InfiniBand 상태를 확인하고 담당 SE 확인을 받아 종결합니다.

주말을 포함한 달력 시간으로 보면 GPU 교체는 접수부터 종결까지 중앙값 24.5시간이었고, 10건 중 1건은 3.7일 넘게 걸렸습니다. 같은 GPU 노드의 광모듈 장애는 중앙값 1.2시간이었습니다.

## 교체하면 끝나는가

GPU를 교체한 노드는 257대였습니다. 이 중 18대는 10개월 동안 GPU를 두 번 이상 교체했고, 가장 많은 노드는 네 번이었습니다.

- GPU 교체 후 30일 안에 같은 노드로 장애가 다시 접수된 비율은 8%, 그중 GPU를 다시 교체한 비율은 5%였습니다.
- 90일로 넓히면 각각 11%, 7%였습니다.
- 장애가 난 GPU 노드 1,152대 중 상위 10%가 장애의 26%를 차지했습니다. CPU 노드는 22%라서, 특정 노드에 몰리는 정도는 크게 다르지 않았습니다.

교체 후 재발한 건은 같은 slot에서 다시 나는지, 다른 GPU에서 나는지를 같이 봐야 했습니다. 같은 slot이면 GPU보다 baseboard나 PCIe 경로를 의심했습니다.

## 규모로 보면

티켓에는 장비 대수가 없어서 장애 기록으로 역산했습니다. 10개월 동안 장애 기록에 한 번이라도 나온 GPU 노드는 1,180대였고, 대부분 8-GPU 서버라 GPU는 9,400장 이상입니다. 장애가 없던 노드는 빠져 있으니 실제 규모는 이보다 큽니다.

- 이 하한으로 계산하면 GPU 교체율은 연 3.7% 이하입니다. 10개월 동안 288장을 교체했고, 연으로 환산하면 약 350장입니다.
- 같은 방식으로 보면 CPU 노드는 9,600대 이상이 장애 기록에 나왔습니다.

## 운영하면서 바꾼 것

- 예비 부품: GPU 노드는 부품을 기다리느라 다시 방문하는 경우가 있었고, CPU 노드도 예비 부품이 있어야 당일에 끝났습니다. 부품 대기와 재방문을 줄이려고 예비 부품 확보를 요청했습니다.
- SLA 대시보드: 장애 처리 SLA를 실제 운영 데이터로 계산하는 [대시보드](/work/idc-ops-digital/)를 만들었습니다. 이 글의 분석도 대시보드가 쓰는 장애 기록에서 데이터를 받아 했습니다.

## 운영하면서 정리한 것

- CPU 노드는 알람이 곧 티켓이었지만, GPU 노드는 담당 SE가 노드 분리 일정을 잡아야 현장 작업이 시작됐습니다. GPU 노드 처리 시간은 현장 작업보다 이 앞단에서 더 많이 정해졌습니다.
- CPU 노드의 가용성은 예비 부품 재고와 현장 대응 속도로 정해졌습니다. GPU 노드는 셧다운 일정을 얼마나 빨리 잡는지, 벤더 판정과 부품 수급이 얼마나 걸리는지로 정해졌습니다.
- GPU 노드는 처리 시간을 줄이려면 현장 작업보다 앞단을 줄여야 했습니다. 담당 SE와 노드 분리 절차를 미리 맞춰 두는 것, 진단에 필요한 로그를 처음 방문에서 다 모으는 것이 여기에 해당합니다.
- GPU 교체는 F/W 기준 버전을 맞추는 것까지가 교체였습니다. 부품만 바꾸면 노드마다 버전이 달라집니다.
- GPU 장애 485건 중 281건은 티켓에 Xid나 증상이 자세히 남아 있지 않았습니다. Xid 번호와 dcgmi 결과를 티켓에 남기는 것만으로도 다음 분석이 훨씬 쉬워질 것 같습니다.
- 처음에는 일부 사이트의 3개월치만 봤는데, 그때는 GPU 노드의 1순위 부위가 GPU였습니다. 10개월치로 넓히니 광모듈이 1순위였습니다. GPU 노드 장애는 기종과 시기에 몰려서, 짧게 보면 경향을 잘못 읽을 수 있었습니다.

## 데이터와 분류 기준

| 항목 | 내용 |
|---|---|
| 기간 | 처리완료 2026.01.01 – 2026.10.26 |
| 대상 | 서버 장애 티켓 약 14,500건 (네트워크, 스토리지 장비 제외) |
| CPU 노드 | 일반 서버, 가상화 호스트, 컨테이너 호스트, 스토리지용 서버 |
| GPU 노드 | 8-GPU H100/H200 서버, A100 서버, HGX 8-GPU 서버, 이전 세대 GPU 서버 |
| 분석 단위 | 같은 이벤트로 반복 등록된 티켓을 하나로 묶은 고유 건 (CPU 11,714건, GPU 1,740건) |

- 티켓에 GPU와 CPU를 구분하는 칸이 없어서 서버 모델로 나눴습니다.
- 부품 교체나 재장착 기록이 있으면 HW 장애, F/W 업데이트나 reboot, power drain만으로 끝났으면 SW 장애로 봤습니다. 처리 유형과 처리 내역의 키워드로 판정해서 몇 % 정도는 오차가 있을 수 있습니다. HW 장애 비율은 CPU 노드 79%, GPU 노드 83%였습니다.
- 장비 대수는 장애 기록에 나온 노드 수로 하한만 알 수 있습니다. 다른 비율은 모두 각 노드 종류 안에서의 비율입니다.
