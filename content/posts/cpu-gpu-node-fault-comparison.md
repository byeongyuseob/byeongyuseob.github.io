> 2026.01 – 2026.10 장애 기록, 2026.10.27 분석. 관련 프로젝트: [서버 Fleet 하드웨어 운영](/work/hardware-troubleshooting/)

## 요약

같은 사이트에서 CPU 노드와 GPU 노드를 같이 운영하고 있습니다. 10개월 동안 현장 처리한 서버 장애 티켓 약 1만 4천 건을 두 종류로 나눠 보니, 고장 나는 곳도 처리하는 방식도 달랐습니다.

CPU 노드 장애는 Disk 같은 소모성 부품이 대부분이라 현장 예비 부품으로 당일에 끝나는 일이 많았습니다. GPU 노드 장애는 GPU와 GPU 네트워크에 몰려 있었고, 부품을 바꾸는 시간보다 노드를 서비스에서 빼고, 진단하고, 벤더 승인을 받는 시간이 더 길었습니다. GPU 노드에는 CPU 노드에서 볼 수 없는 장애 유형도 따로 있었습니다.

GPU 노드는 HW 장애 때문에 평균 5대 안팎이 늘 서비스에서 빠져 있었고, 많은 날은 10대가 넘었습니다. 이 숫자를 바탕으로 다음에 GPU 클러스터를 설계한다면 먼저 검토할 것을 마지막에 정리했습니다.

## 고장 나는 곳이 다르다

| 부위 (HW 장애 중 비율) | CPU 노드 | GPU 노드 |
|---|---|---|
| Disk | 약 50% | 약 10% |
| NIC, 광모듈, 케이블 | 약 15% | 약 50% |
| GPU | - | 약 25% |
| Memory | 약 15% | 5% 미만 |
| FAN | 약 5% | 1% 안팎 |
| PSU | 약 5% | 약 10% |

CPU 노드는 디스크를 많이 꽂는 스토리지용 서버가 많아서 장애의 절반 가까이가 Disk였습니다. 교체한 디스크 대부분이 3.5인치 HDD였고, 거의 모두 현장 예비 부품으로 바로 바꿨습니다.

GPU 노드는 한 대에 GPU 8장, GPU 사이를 잇는 NVSwitch, 고속 NIC 여러 장과 그만큼의 InfiniBand 광모듈이 들어갑니다. 고장 날 수 있는 큰 부품이 GPU와 GPU 네트워크 쪽에 몰려 있어서 장애도 그쪽에서 났습니다.

GPU 노드 안에서도 세대에 따라 구성이 달랐습니다. 장비 대수를 알 수 없어서 고장률 비교는 못 하고, 장애 구성만 비교했습니다.

| GPU 노드 세대 | HW 장애 1순위 | 2순위 |
|---|---|---|
| H100/H200급 8-GPU | NIC, 광모듈 (약 55%) | GPU (약 25%) |
| HGX 8-GPU | GPU (약 40%) | NIC, 광모듈 (약 30%) |
| A100급 8-GPU | GPU (약 40%) | NIC, 광모듈 (약 15%) |
| 이전 세대 GPU 서버 | PSU, GPU, NIC가 비슷 (각 약 20%) | |

## GPU 서버에만 있는 장애

GPU Error로 들어온 약 500건을 티켓에 적힌 증상으로 나눴습니다.

| 증상 | 대략 건수 | 주로 한 처리 |
|---|---|---|
| GPU 미인식 (Missing, Xid 79, device handle error) | 약 100 | GPU 교체, 일부는 swap 후 baseboard 교체 |
| ECC, Remapped Row, SRAM error | 약 30 | GPU 교체 |
| 비정상 온도 | 약 25 | GPU 교체 |
| PCIe Fatal, Downtrain | 약 10 | 재장착 또는 swap |
| NVLink, NVSwitch error | 약 10 | GPU 교체 |
| 그 밖의 Xid | 약 30 | swap 또는 교체 |
| 증상 상세 기록 없음 | 약 280 | GPU 교체, swap |

절반이 넘는 건은 티켓에 Xid 번호나 증상이 자세히 남아 있지 않아서, 위 표는 기록이 남은 건 위주로 읽어야 합니다. CPU 노드에서는 없는 유형들이고, 운영하면서 느낀 특징은 아래와 같습니다.

- GPU 1장이 문제여도 노드 전체를 내려야 합니다. GPU는 hot swap이 안 되고, 진단도 OS를 끈 상태에서 해야 해서 나머지 7장도 같이 멈춥니다.
- 온도가 교체 근거가 됩니다. GPU 교체의 약 4분의 1은 벤더 온도 수집 프로그램으로 온도가 비정상인 GPU를 찾아 바꾼 건이었습니다. CPU 노드에는 온도를 근거로 부품을 바꾼 기록이 없었습니다.
- Xid라고 모두 HW 장애는 아닙니다. Xid 94(GPU 안에서 처리된 correctable ECC)와 137(GSP 응답 없음)이 같이 나온 건에서, 벤더는 모든 GPU에 ECC error 이력이 없는 것을 확인하고 application 단 에러로 판단했습니다. application 재실행과 GPU reset, power cycle 후 모니터링으로 종결했습니다. 반대로 Xid 79처럼 GPU가 bus에서 떨어진 경우는 교체로 이어졌습니다.
- 증상이 slot을 따라가는지 봐야 합니다. 의심 GPU를 다른 slot의 GPU와 바꿔 끼워서, 증상이 GPU를 따라가면 GPU 불량, slot에 남으면 baseboard나 PCIe 경로 쪽으로 봤습니다. GPU 교체의 약 3분의 1이 이 swap test를 거쳤습니다.
- InfiniBand 광모듈 장애가 많고 몰려서 납니다. GPU 노드 NIC 장애 약 700건 중 약 400건이 한 사이트의 같은 8-GPU 기종에서 나왔고, 대부분 광모듈 교체였습니다. link down 알람을 받으면 서버 쪽 트랜시버와 스위치 쪽 포트를 같이 확인하고, 필요하면 옆 포트와 교차해 원인 위치를 찾은 뒤 GBIC이나 케이블을 바꿨습니다.
- 이 광모듈 장애는 1월 약 130건에서 10월 약 20건으로 줄었습니다. 초기 불량이 걸러진 것과, 클러스터 용도가 학습에서 추론으로 넘어가면서 노드 사이 InfiniBand 통신이 줄어든 영향으로 보고 있습니다. 용도 전환 시점과 정확히 맞춰 보지는 못했습니다.

## 장애가 접수되는 방식

장애는 두 종류 노드 모두 전사 모니터링 시스템으로 감지됩니다. 차이는 그 다음이었습니다.

| 접수 경로 | CPU 노드 | GPU 노드 |
|---|---|---|
| 모니터링 알람이 바로 티켓으로 | 약 70% | 약 25% |
| 담당 SE가 확인 후 접수 | 약 25% | 약 75% |
| 그 외 | 약 5% | 1% 미만 |

CPU 노드는 Disk Error, Ping Fail 같은 알람이 바로 티켓이 되고, 현장에서 부품을 바꾸면 끝났습니다. GPU 노드는 GPU 교체의 약 70%, 광모듈 장애의 95% 가까이를 담당 SE가 접수했습니다. GPU 노드는 서비스에서 빼야 작업할 수 있어서, 담당 SE가 노드 분리 일정을 계획하고 서비스에서 제외한 뒤 현장에 넘기는 흐름이었습니다.

## 같은 알람, 다른 원인

Ping Fail은 두 종류 노드 모두에서 자주 오는 알람인데, 뒤에 있는 원인이 달랐습니다.

- CPU 노드의 Ping Fail은 Memory가 가장 많았고 CPU, Mainboard 순서였습니다. BMC 로그에서 Machine Check Exception이나 uncorrectable memory error를 찾는 것으로 시작했습니다.
- GPU 노드의 Ping Fail은 PCIe bus fatal error, DPC error처럼 PCIe switch 아래 GPU나 NIC slot에서 시작된 장애가 서버 다운으로 이어진 경우가 많았습니다. 과열로 system down 된 건도 있었습니다.

같은 알람이 와도 노드 종류에 따라 처음 볼 로그가 달랐습니다.

## 처리 방식이 다르다

| 항목 | CPU 노드 | GPU 노드 |
|---|---|---|
| 벤더 점검을 거친 비율 (HW 장애) | 약 15% | 약 60% |
| 현장 예비 부품 사용 기록 (HW 장애) | 약 65% | 약 15% |
| F/W 업데이트 동반 | 약 15% | 약 25% |
| 대표 장애의 처리 시간 | Disk 약 7시간 | 광모듈 약 1시간, GPU 교체 약 하루 |

CPU 노드는 현장에 둔 예비 부품으로 운영팀이 판단하고 바로 바꿨습니다. GPU 교체는 예비 부품을 쓴 기록이 거의 없었고, 대부분 벤더 엔지니어의 로그 분석으로 교체 승인을 받은 뒤 부품을 받아서 바꿨습니다. 부품이 없어서 다시 방문한 경우가 GPU 교체의 약 15%였습니다.

GPU 교체 1건은 아래 순서로 진행했고, 부품을 바꾸는 시간은 이 중 일부였습니다.

1. 담당 SE가 노드 분리 일정을 계획하고 서비스에서 제외한 뒤 셧다운합니다.
2. AC power cycle 후 BMC 로그와 nvidia-bug-report를 수집합니다.
3. 벤더 온도 수집 프로그램, `dcgmi diag -r 3`, field diagnostic을 돌립니다. 셧다운 일정이 안 잡히면 진단 자체를 못 해서, 열흘 넘게 보류하다 종결한 건도 있었습니다.
4. swap test로 GPU 불량인지 slot 쪽인지 가립니다.
5. 벤더 승인을 받고 GPU를 교체합니다.
6. BIOS, BMC, GPU baseboard, PCIe switch, CPLD, NIC F/W를 기준 버전으로 맞춥니다. GPU 교체의 90% 가까이에서 F/W 업데이트를 같이 했습니다.
7. GPU 8장 인식, dcgmi diag 통과, NVLink와 NVSwitch와 InfiniBand 상태를 확인하고 담당 SE 확인을 받아 종결합니다.

주말을 포함한 달력 시간으로 보면 GPU 교체는 접수부터 종결까지 약 하루였고, 10건 중 1건은 4일 가까이 걸렸습니다. 이 시간은 티켓 접수부터 잰 것이라, 장애가 난 뒤 담당 SE가 노드를 분리하고 접수하기까지의 시간은 빠져 있습니다. 서비스가 실제로 GPU를 못 쓴 시간은 이보다 깁니다.

## 서비스에서 빠진 GPU 노드

티켓의 접수와 종결 시각으로, GPU 노드가 장애 처리 때문에 서비스에서 빠져 있던 시간을 계산했습니다. 같은 노드에 티켓이 겹치면 한 번만 셌습니다.

| 원인 | 10개월 합계 | 평균 동시 이탈 |
|---|---|---|
| GPU 노드 HW 장애 전체 | 약 3만 4천 node-hour (약 27만 GPU-hour) | 약 5대 |
| 그중 GPU 교체 | 약 1만 3천 node-hour | 약 2대 |
| 그중 광모듈, NIC | 약 7천 node-hour | 약 1대 |

날마다 보면 HW 장애로 빠진 GPU 노드는 보통 6대 안팎이었고, 많은 날은 10대가 넘었고, 가장 많은 날은 20대를 넘었습니다. 접수 전 시간이 빠져 있으니 실제로는 이보다 많습니다.

## 교체하면 끝나는가

GPU를 교체한 노드는 약 260대였습니다. 이 중 약 20대는 10개월 동안 GPU를 두 번 이상 교체했고, 가장 많은 노드는 네 번이었습니다.

- GPU 교체 후 30일 안에 같은 노드로 장애가 다시 접수된 비율은 10% 미만, 그중 GPU를 다시 교체한 비율은 약 5%였습니다. 90일로 넓히면 각각 약 10%, 약 7%였습니다.
- 장애가 난 노드 중 상위 10%가 장애에서 차지하는 비율은 GPU 노드 약 25%, CPU 노드 약 20%로 크게 다르지 않았습니다.

교체 후 재발한 건은 같은 slot에서 다시 나는지, 다른 GPU에서 나는지를 같이 봐야 했습니다. 같은 slot이면 GPU보다 baseboard나 PCIe 경로를 의심했습니다.

## 운영하면서 바꾼 것

- 예비 부품: GPU 노드는 부품을 기다리느라 다시 방문하는 경우가 있었고, CPU 노드도 예비 부품이 있어야 당일에 끝났습니다. 부품 대기와 재방문을 줄이려고 예비 부품 확보를 요청했습니다.
- SLA 대시보드: 장애 처리 SLA를 실제 운영 데이터로 계산하는 [대시보드](/work/idc-ops-digital/)를 만들었습니다. 이 글의 분석도 대시보드가 쓰는 장애 기록에서 데이터를 받아 했습니다.

## 운영하면서 정리한 것

- CPU 노드의 가용성은 예비 부품 재고와 현장 대응 속도로 정해졌습니다. GPU 노드는 노드 분리 일정, 벤더 판정, 부품 수급 같은 현장 작업 앞단에서 처리 시간이 더 많이 정해졌습니다.
- GPU 교체는 F/W 기준 버전을 맞추는 것까지가 교체였습니다. 부품만 바꾸면 노드마다 버전이 달라집니다.
- GPU 장애의 절반 이상은 Xid나 증상 기록이 부족했습니다. Xid 번호와 dcgmi 결과를 티켓에 남기는 것만으로도 다음 분석이 훨씬 쉬워질 것 같습니다.
- 처음에는 일부 사이트의 3개월치만 봤는데, 그때는 GPU 노드의 1순위 부위가 GPU였습니다. 10개월치로 넓히니 광모듈이 1순위였습니다. GPU 노드 장애는 기종과 시기에 몰려서, 짧게 보면 경향을 잘못 읽을 수 있었습니다.

## 다음 GPU 클러스터라면 먼저 검토할 것

운영 데이터로 보면 아래를 설계 단계에서 먼저 정해 두는 것이 좋겠다고 생각합니다.

- 예비 노드: GPU 노드가 평균 5대, 많은 날 10대 넘게 빠져 있었습니다. 부품 예비만으로는 이 공백을 못 메우니, 처음부터 용량의 일부를 예비 노드로 잡아 두고 장애 노드는 빼서 고치는 방식을 검토하겠습니다.
- 노드 분리 절차: GPU 노드 처리 시간은 분리 일정에서 많이 결정됐습니다. 장애 노드를 서비스에서 빼는 기준과 걸리는 시간을 서비스 쪽과 운영 쪽이 미리 합의해 두겠습니다.
- 감지 지표: 접수 전 시간을 잴 수 없었던 것이 이번 분석의 한계였습니다. 장애 발생, 노드 분리, 접수, 종결 시각이 각각 남도록 하고, Xid와 dcgmi 결과가 티켓에 자동으로 붙게 하겠습니다.
- F/W 기준 버전: 교체 때마다 F/W를 맞췄으니, 기종별 기준 버전을 운영 표준으로 두고 투입과 교체 때 같은 기준으로 점검하겠습니다.
- 광모듈 투입 검증: 연초에 광모듈 장애가 한 기종에 몰렸다가 줄었습니다. 초기 불량이었다면 투입 전 burn-in과 link 품질 점검으로 일부를 미리 걸러낼 수 있었을 것입니다.

- 티켓에 GPU와 CPU를 구분하는 칸이 없어서 서버 모델로 나눴습니다.
- 부품 교체나 재장착 기록이 있으면 HW 장애, F/W 업데이트나 reboot, power drain만으로 끝났으면 SW 장애로 봤습니다. 처리 유형과 처리 내역의 키워드로 판정해서 몇 % 정도는 오차가 있을 수 있습니다. HW 장애는 두 종류 노드 모두 약 80%였습니다.
- 장비 대수는 티켓에 없어서 고장률은 계산하지 않았습니다. 비율은 모두 각 노드 종류 안에서의 비율입니다.
