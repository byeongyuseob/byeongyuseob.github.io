> 2026.07 – 2026.10 장애 기록, 2026.10.27 분석. 관련 프로젝트: [서버 Fleet 하드웨어 운영](/work/hardware-troubleshooting/)

## 요약

제가 근무하는 사이트에서 현장 처리한 서버 장애 티켓 3개월치(약 1,390건)를 CPU 노드와 GPU 노드로 나눠 분류하고 분석했습니다.

CPU 노드는 HDD와 NIC 쪽 부품이 HW 장애의 59%였고, 현장 예비 부품으로 바로 교체하는 건이 많았습니다. GPU 노드는 GPU 자체가 HW 장애의 44%로 가장 많았고, 벤더 점검을 거친 비율도 72%로 CPU 노드(43%)보다 높았습니다. 처리 시간 중앙값은 GPU 노드가 더 짧았지만, GPU를 교체하는 건은 진단과 승인 단계가 길고 부품을 기다리느라 다시 방문한 경우가 22%였습니다.

## 데이터와 분류 기준

| 항목 | 내용 |
|---|---|
| 기간 | 2026.07.27 – 2026.10.26 |
| 대상 | 서버 장애 티켓 약 1,390건 (네트워크, 스토리지 장비 제외) |
| CPU 노드 | 일반 서버, 가상화 호스트, 컨테이너 호스트 |
| GPU 노드 | 8-GPU H100/H200 서버, A100 서버, HGX 8-GPU 서버 |
| 분석 단위 | 같은 이벤트로 반복 등록된 티켓을 하나로 묶은 고유 건 (CPU 620건, GPU 306건) |

- 티켓에 GPU와 CPU를 구분하는 칸이 없어서 서버 모델로 나눴습니다.
- 부품 교체나 재장착 기록이 있으면 HW 장애, F/W 업데이트나 BIOS 설정, reboot, power drain만으로 끝났으면 SW 장애로 봤습니다. 처리 유형과 처리 내역의 키워드로 판정해서 몇 % 정도는 오차가 있을 수 있습니다.
- 장비 대수 대비 고장률은 이 데이터로 알 수 없습니다. 아래 비율은 모두 각 노드 종류 안에서의 비율입니다.

| 판정 | CPU 노드 | GPU 노드 |
|---|---|---|
| HW 장애 | 456건 (74%) | 255건 (83%) |
| SW 장애 | 52건 (8%) | 20건 (7%) |
| 계획 작업 중 알람 | 12건 (2%) | 0건 |
| 확인 후 종결 | 100건 (16%) | 31건 (10%) |

## 어느 부위에서 많이 나는가

HW 장애를 실제로 교체하거나 재장착한 부품 기준으로 다시 셌습니다.

| 부위 | CPU 노드 (456건) | GPU 노드 (255건) |
|---|---|---|
| GPU | - | 113건 (44%) |
| Disk | 153건 (34%) | 21건 (8%) |
| NIC, 광모듈, 케이블 | 115건 (25%) | 68건 (27%) |
| Memory | 62건 (14%) | 10건 (4%) |
| CPU | 37건 (8%) | 6건 (2%) |
| Mainboard | 34건 (7%) | 6건 (2%) |
| RAID Controller | 27건 (6%) | 0건 |
| PSU | 17건 (4%) | 26건 (10%) |
| FAN | 9건 (2%) | 0건 |

GPU 노드는 한 대에 GPU 8장과 고속 NIC 여러 장, 그만큼의 광모듈이 들어갑니다. 고장 날 수 있는 큰 부품이 CPU 노드보다 많고, 그 대부분이 GPU와 GPU 네트워크 쪽이라 장애도 그쪽에 몰렸습니다.

## CPU 노드의 주요 원인과 처리

- Disk (34%): 교체 부품 기록을 보면 대부분 8TB에서 24TB 사이의 3.5인치 대용량 HDD였습니다. HW 장애 건의 41%는 현장에 둔 예비 부품으로 바로 교체했습니다.
- NIC (25%): GBIC 교체와 케이블 재탈착이 대부분이었습니다. 스위치 장애나 스위치 cold reboot 뒤에 연결된 서버들이 한꺼번에 NIC 알람을 올린 경우도 있었고, 이때는 서버 쪽에 이상이 없어 확인만 하고 종결했습니다.
- Ping Fail: 증상 기준으로는 CPU 노드 장애의 35%로 가장 많지만, 증상 이름만으로는 원인을 알 수 없습니다. HW로 판정된 Ping Fail을 부품별로 보면 Memory 34건, CPU 26건, Mainboard 26건, RAID Controller 13건 순서였습니다. BMC 로그에서 Machine Check Exception이나 uncorrectable memory error를 확인하고, 벤더 점검 후 부품 교체와 F/W 업데이트를 같이 했습니다.
- SW 장애: OS hang은 power drain이나 cold reboot로 살렸고, 일부는 부품 교체 없이 F/W 업데이트만으로 끝났습니다.
- 계획 작업 알람: 고유 건으로는 12건이지만 티켓으로는 183건, CPU 노드 티켓의 17%였습니다. OS 재설치 같은 계획 작업에 걸린 서버들이 한꺼번에 알람을 올린 것입니다.

## GPU 노드의 주요 원인과 처리

GPU 자체 장애는 티켓에 적힌 증상 기준으로 아래와 같았습니다 (GPU Error 122건).

| 기록된 증상 | 건수 | 주된 처리 |
|---|---|---|
| GPU 미인식 (Missing, Xid 79, device handle error) | 24 | GPU 교체 17, Board 교체 3 |
| 비정상 온도 | 14 | 모두 GPU 교체 |
| ECC, Remapped Row, SRAM error | 6 | GPU 교체 3, swap 2 |
| PCIe Fatal, Downtrain | 6 | 재장착 또는 swap 4 |
| NVLink, NVSwitch error | 3 | GPU 교체 2 |
| 증상 상세 기록 없음 | 64 | GPU 교체 37, swap 13 |

- 온도 판정: GPU를 교체한 86건 중 37건(43%)은 벤더 온도 수집 프로그램으로 온도가 비정상인 GPU를 찾아 교체한 건이었습니다. 온도 로그가 교체 판단의 가장 흔한 근거였습니다.
- Ping Fail과 Down: GPU 노드에서는 PCIe bus fatal error, DPC error처럼 PCIe switch 아래 GPU나 NIC slot에서 시작된 장애가 서버 다운으로 이어진 경우가 많았습니다. 과열로 system down 된 건도 있었습니다.
- NIC와 광모듈 (27%): InfiniBand 400G 광모듈과 고속 NIC의 link down, link flap이었습니다. 트랜시버를 옆 포트와 바꿔 끼워 원인 위치를 확인하고 GBIC이나 케이블을 교체했습니다. 페어 서버와 케이블이 바뀌어 꽂힌 경우도 있었습니다. 처리 시간 중앙값은 1시간으로 짧았습니다.
- PSU (10%): 같은 기종에서 하루에 여러 대의 PSU를 교체한 날이 있었습니다.
- SW 장애: Xid 94, 137은 벤더가 ECC error 이력이 없음을 확인하고 application 재실행과 GPU reset을 권고해서 교체 없이 종결했습니다. Xid 109는 모니터링으로 종결했고, power drain만으로 복구한 건이 4건 있었습니다.

## 처리 절차의 차이

| 항목 | CPU 노드 | GPU 노드 |
|---|---|---|
| 벤더 점검을 거친 비율 (HW 장애) | 43% | 72% |
| 현장 예비 부품 사용 기록 (HW 장애) | 41% | 13% |
| F/W 업데이트 동반 (전체 티켓) | 16% | 39% |
| 처리 시간 중앙값 (고유 건) | 17시간 | 9시간 |
| 당일 완료 비율 (고유 건) | 39% | 51% |

GPU 노드 전체로는 NIC 장애처럼 빨리 끝나는 건이 많아서 중앙값이 짧았습니다. GPU를 교체한 건만 보면 처리 시간 중앙값이 23시간이었고, 아래 단계를 거쳤습니다.

1. 서비스 담당자가 workload를 내리고 셧다운합니다. 페어 장비가 있으면 서비스에서 먼저 뺍니다.
2. AC power cycle 후 BMC 로그와 nvidia-bug-report를 수집합니다.
3. 벤더 온도 수집 프로그램, `dcgmi diag -r 3`, field diagnostic을 돌립니다. 온도 수집 프로그램은 OS가 꺼진 상태에서만 돌아서, 셧다운 일정이 안 잡히면 진단 자체를 못 합니다. 일정이 잡히지 않아 12일 동안 보류하다 종결한 건도 있었습니다.
4. 의심 GPU를 다른 slot의 GPU와 바꿔 끼우는 swap test로 원인 위치를 가립니다. 증상이 GPU를 따라가면 GPU 불량이고, slot에 남으면 baseboard나 PCIe 경로 쪽입니다. GPU 교체 건의 31%에서 이 과정을 거쳤습니다.
5. 벤더 엔지니어의 로그 분석으로 교체 승인을 받습니다. 부품이 없으면 수급 후 다시 방문했고, 이런 경우가 22%였습니다.
6. GPU를 교체하면서 BIOS, BMC, GPU baseboard, PCIe switch, CPLD, NIC F/W를 기준 버전으로 맞춥니다. GPU 교체 건의 91%에서 F/W 업데이트를 같이 했습니다.
7. GPU 8장 인식, dcgmi diag 통과, NVLink와 NVSwitch와 InfiniBand 상태를 확인하고 서비스 담당자 확인을 받아 종결합니다.

## 정리

- CPU 노드 장애는 HDD, NIC 같은 부품이 많고 현장 예비 부품으로 바로 끝나는 경우가 많았습니다. Ping Fail 뒤에는 Memory, CPU, Mainboard 장애가 있는 경우가 많아서 BMC 로그부터 확인해야 했습니다.
- GPU 노드 장애는 GPU와 GPU 네트워크에 몰려 있었습니다. GPU 교체 건은 셧다운 조율, 오프라인 진단, swap test, 벤더 승인, F/W 맞춤까지 단계가 많고, 5건 중 1건은 부품 때문에 한 번에 끝나지 않았습니다.
- GPU 교체 1건은 GPU 노드 1대를 하루 가까이 서비스에서 빼는 일이었습니다.
