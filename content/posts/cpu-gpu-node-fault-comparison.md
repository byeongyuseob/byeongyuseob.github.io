> 2026.01 – 2026.10 장애 기록, 2026.10.27 분석. 관련 프로젝트: [서버 Fleet 하드웨어 운영](/work/hardware-troubleshooting/)

## 요약

같은 사이트에서 CPU 노드와 GPU 노드를 같이 운영하면서, 10개월 동안 현장 처리한 서버 장애 티켓 약 1만 4천 건을 두 종류로 나눠 봤습니다.

- 고장 나는 곳: CPU 노드는 Disk, GPU 노드는 GPU와 InfiniBand 광모듈이었습니다.
- 더 큰 차이는 처리 시간이었습니다. CPU 노드는 현장 예비 부품으로 당일에 끝났고, GPU 노드는 노드 분리, 진단, 벤더 승인을 거쳐 GPU 교체 1건에 약 하루가 걸렸습니다.
- 그 결과 GPU 노드는 평균 5대 안팎이 늘 서비스에서 빠져 있었습니다. 다음 GPU 클러스터라면 예비 노드와 노드 분리 절차를 설계 단계에서 먼저 정하겠습니다.

## 왜 나눠 봤나

같은 현장에서 두 종류 노드를 같이 맡다 보면, 같은 "서버 장애"라도 GPU 노드는 일하는 방식이 다르다는 것을 느낍니다. 디스크 하나 바꾸면 끝나는 CPU 노드와 달리, GPU 노드는 담당 SE와 일정을 맞추고 벤더와 로그를 주고받는 시간이 길었습니다.

이 차이가 실제 기록에서도 보이는지, 보인다면 어디서 얼마나 나는지 확인하려고 10개월치 장애 티켓을 서버 모델 기준으로 CPU 노드와 GPU 노드로 나눠 분석했습니다.

## 고장 나는 곳이 다르다

| 부위 (HW 장애 중 비율) | CPU 노드 | GPU 노드 |
|---|---|---|
| Disk | 약 50% | 약 10% |
| NIC, 광모듈, 케이블 | 약 15% | 약 50% |
| GPU | - | 약 25% |
| Memory | 약 15% | 5% 미만 |
| PSU | 약 5% | 약 10% |

CPU 노드는 디스크를 많이 꽂는 스토리지용 서버가 많아서 장애의 절반 가까이가 Disk였고, 거의 모두 현장 예비 부품으로 바로 바꿨습니다.

GPU 노드는 한 대에 GPU 8장, NVSwitch, 고속 NIC 여러 장과 그만큼의 InfiniBand 광모듈이 들어갑니다. 고장 날 수 있는 큰 부품이 GPU와 GPU 네트워크에 몰려 있어서 장애도 그쪽에서 났습니다. 세대별로는 H100/H200급이 광모듈 쪽, A100급과 HGX 8-GPU 서버는 GPU 쪽 장애가 더 많았습니다.

## GPU 노드에만 있는 장애

GPU Error로 들어온 약 500건 중 증상이 기록된 건을 보면 GPU 미인식(Xid 79, Missing)이 가장 많았고, ECC와 Remapped Row, 비정상 온도, PCIe Fatal, NVLink와 NVSwitch error가 뒤를 이었습니다. 처리하면서 CPU 노드와 다르다고 느낀 점은 다섯 가지였습니다.

- GPU 1장 때문에 노드 전체가 멈춥니다. GPU는 hot swap이 안 되고 진단도 OS를 끈 상태에서 해야 해서, 나머지 7장도 같이 서비스에서 빠집니다.
- 온도가 교체 근거가 됩니다. GPU 교체의 약 4분의 1은 벤더 온도 수집 프로그램으로 비정상 GPU를 찾아 바꾼 건이었습니다. CPU 노드에는 이런 기록이 없었습니다.
- Xid 번호와 ECC 이력을 먼저 봐야 합니다. Xid 94(contained correctable ECC)와 137(GSP 응답 없음)이 같이 나온 건은 모든 GPU에 ECC error 이력이 없어서, 벤더가 application 단 에러로 판단하고 재실행과 GPU reset으로 종결했습니다. Xid 79처럼 GPU가 bus에서 떨어진 경우는 교체로 이어졌습니다.
- 원인 위치를 swap test로 가립니다. 의심 GPU를 다른 slot과 바꿔 끼워 증상이 GPU를 따라가면 GPU 불량, slot에 남으면 baseboard나 PCIe 경로 쪽으로 봤습니다. GPU 교체의 약 3분의 1이 이 과정을 거쳤습니다.
- 같은 Ping Fail이라도 원인이 다릅니다. CPU 노드는 Memory, CPU, Mainboard 장애였고 BMC 로그의 Machine Check Exception부터 봤습니다. GPU 노드는 PCIe switch 아래 GPU나 NIC slot에서 시작된 bus fatal error, DPC error가 서버 다운으로 이어진 경우가 많았습니다.

InfiniBand 광모듈은 GPU 노드 NIC 장애 약 700건 중 약 400건이 한 사이트의 같은 기종에서 나왔습니다. 서버 쪽 트랜시버와 스위치 쪽 포트를 같이 확인하고, 필요하면 옆 포트와 교차해 위치를 찾은 뒤 바꿨습니다. 1월 약 130건에서 10월 약 20건으로 줄었는데, 초기 불량이 걸러진 것과 클러스터 용도가 학습에서 추론으로 넘어가며 노드 사이 통신이 줄어든 영향으로 보고 있습니다.

## 차이는 처리 시간에서 더 컸다

부품보다 더 크게 달랐던 것은 장애 하나를 끝내는 데 드는 시간과 단계였습니다.

### 접수부터 다르다

장애는 두 종류 모두 전사 모니터링 시스템으로 감지됩니다. CPU 노드는 장애의 약 70%가 알람에서 바로 티켓이 됐고, GPU 노드는 약 75%를 담당 SE가 확인하고 노드 분리 일정을 잡은 뒤 접수했습니다. GPU 노드는 서비스에서 빼야 작업할 수 있기 때문입니다.

### GPU 교체 1건의 순서

1. 담당 SE가 노드 분리 일정을 계획하고 서비스에서 제외한 뒤 셧다운합니다.
2. AC power cycle 후 BMC 로그와 nvidia-bug-report를 수집합니다.
3. 벤더 온도 수집 프로그램, `dcgmi diag -r 3`, field diagnostic을 돌립니다. 셧다운 일정이 안 잡혀 열흘 넘게 보류된 건도 있었습니다.
4. swap test로 GPU 불량인지 slot 쪽인지 가립니다.
5. 벤더 승인을 받고 GPU를 교체합니다. 예비 부품을 쓴 기록은 거의 없었고, 부품이 없어 다시 방문한 경우가 약 15%였습니다.
6. BIOS, BMC, GPU baseboard, PCIe switch, CPLD, NIC F/W를 기준 버전으로 맞춥니다. GPU 교체의 90% 가까이에서 같이 했습니다.
7. GPU 8장 인식, dcgmi diag, NVLink와 NVSwitch와 InfiniBand 상태를 확인하고 담당 SE 확인을 받아 종결합니다.

| 항목 | CPU 노드 | GPU 노드 |
|---|---|---|
| 벤더 점검을 거친 비율 (HW 장애) | 약 15% | 약 60% |
| 현장 예비 부품 사용 기록 (HW 장애) | 약 65% | 약 15% |
| 대표 장애의 처리 시간 | Disk 약 7시간 | 광모듈 약 1시간, GPU 교체 약 하루 |

GPU 교체는 달력 시간으로 10건 중 1건이 4일 가까이 걸렸습니다. 이 시간은 티켓 접수부터 잰 것이라, 장애가 난 뒤 노드를 분리하고 접수하기까지의 시간은 빠져 있습니다.

### 그래서 늘 빠져 있는 노드가 있었다

접수와 종결 시각으로 계산하면, 10개월 동안 GPU 노드가 HW 장애로 서비스에서 빠진 시간은 약 3만 4천 node-hour, GPU로는 약 27만 GPU-hour였습니다. 평균으로 약 5대가 늘 빠져 있었고, 많은 날은 10대가 넘었습니다. 그중 GPU 교체가 약 2대, 광모듈이 약 1대 몫이었습니다.

교체한다고 끝나지도 않았습니다. GPU를 교체한 약 260대 중 약 20대는 10개월 안에 GPU를 두 번 이상 바꿨고, 교체 후 90일 안에 같은 노드에서 GPU를 다시 바꾼 비율은 약 7%였습니다. 같은 slot에서 재발하면 GPU보다 baseboard나 PCIe 경로를 의심했습니다.

## 운영에 반영한 것과 다음에 할 것

지금까지 운영에서 바꾼 것은 두 가지입니다.

- 부품 대기와 재방문을 줄이려고 예비 부품 확보를 요청했습니다.
- 장애 처리 SLA를 실제 운영 데이터로 계산하는 [대시보드](/work/idc-ops-digital/)를 만들었습니다. 이 글의 분석도 같은 장애 기록에서 했습니다.

다음 GPU 클러스터를 설계한다면 아래를 먼저 정하겠습니다.

- 예비 노드: 늘 5대 안팎이 빠져 있었으니, 부품 예비만으로는 부족합니다. 처음부터 용량 일부를 예비 노드로 잡고, 장애 노드는 빼서 고치는 방식을 검토하겠습니다.
- 노드 분리 절차: GPU 노드 처리 시간은 분리 일정에서 많이 정해졌습니다. 장애 노드를 빼는 기준과 시간을 서비스 쪽과 미리 합의해 두겠습니다.
- 장애 기록: GPU 장애의 절반 이상은 Xid나 증상 기록이 부족했고, 접수 전 시간도 잴 수 없었습니다. 장애 발생, 노드 분리, 접수, 종결 시각과 Xid, dcgmi 결과가 티켓에 남도록 하겠습니다.
- F/W 기준 버전: 교체 때마다 맞춘 버전을 기종별 운영 표준으로 두고, 투입과 교체 때 같은 기준으로 점검하겠습니다.
- 광모듈 투입 검증: 연초 광모듈 장애가 초기 불량이었다면, 투입 전 burn-in과 link 품질 점검으로 일부를 미리 걸러낼 수 있었을 것입니다.

처음에는 일부 사이트의 3개월치만 봤는데, 그때는 GPU 노드의 1순위 부위가 GPU였습니다. 10개월치로 넓히니 광모듈이 1순위였습니다. GPU 노드 장애는 기종과 시기에 몰려서, 경향을 말할 때는 범위와 기간을 먼저 밝혀야 한다는 것도 이번에 배웠습니다.

## 데이터와 분류 기준

| 항목 | 내용 |
|---|---|
| 기간 | 처리완료 2026.01 – 2026.10 |
| 대상 | 서버 장애 티켓 약 1만 4천 건 (네트워크, 스토리지 장비 제외) |
| CPU 노드 | 일반 서버, 가상화 호스트, 컨테이너 호스트, 스토리지용 서버 |
| GPU 노드 | 8-GPU H100/H200 서버, A100 서버, HGX 8-GPU 서버, 이전 세대 GPU 서버 |
| 분석 단위 | 같은 이벤트로 반복 등록된 티켓을 하나로 묶은 고유 건 |

- 건수와 비율은 반올림한 대략값입니다.
- 티켓에 GPU와 CPU를 구분하는 칸이 없어서 서버 모델로 나눴습니다.
- 부품 교체나 재장착 기록이 있으면 HW 장애, F/W 업데이트나 reboot, power drain만으로 끝났으면 SW 장애로 봤습니다. 키워드로 판정해서 몇 % 정도는 오차가 있을 수 있습니다. HW 장애는 두 종류 모두 약 80%였습니다.
- 노드 이탈 시간은 같은 노드에 티켓이 겹치면 한 번만 셌습니다.
- 장비 대수는 티켓에 없어서 고장률은 계산하지 않았습니다.
