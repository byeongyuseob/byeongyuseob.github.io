> 2019.01 – 2022.10, PM. 관련 프로젝트: [대규모 서버 운영 자동화](/work/ops-automation/)

## 요약

서버 6만 대+ 환경에서 하드웨어·OS 장애가 하루 30~40건 발생했습니다. 2019년에 장애 유형과 표준 절차를 먼저 정리했고, 2021.12부터 2022.10까지 그 유형을 Ansible Playbook으로 옮겨 웹 콘솔에서 실행하게 했습니다. 정형화된 장애는 Playbook 실행 한 번으로 수십 초 안에 처리하게 됐고, 서버 직접 접속은 거의 없어졌습니다.

## 출발점

| 문제 | 영향 |
|---|---|
| 담당자마다 대응 방식이 다름 | 같은 장애도 처리 시간과 결과가 사람에 따라 달라짐 |
| 각자 판단으로 명령어 실행 | 잘못된 명령어로 추가 장애가 생기기도 함 |
| 여러 사람이 서버에 직접 접속 | 보안 위험 |
| 경험이 적은 엔지니어 | 처리가 늦음 |

## 1단계: 유형과 허용 명령어 정하기 (2019)

- 과거 장애 처리 기록과 로그를 분석해 반복되는 유형을 정리했습니다.
- 보안 기준과 컴플라이언스 요구에 맞춰 모든 담당자가 쓸 수 있는 허용 명령어 목록을 정의했습니다.
- 유형별 조치를 매뉴얼로 만들고 교육과 실습을 진행했습니다.

이때 정한 장애 유형이 나중에 Playbook 하나의 단위가 됐습니다.

## 2단계: 유형별 Playbook

- 하드웨어와 OS 장애를 유형별로 나누고, 매뉴얼의 조치를 유형마다 Ansible Playbook으로 옮겼습니다.
- 작업 대상은 Ansible Dynamic Inventory로 사용자가 입력한 서버 정보를 실시간으로 모아 정했습니다. 서버 정보의 원본은 2017년 수집 자동화 때 연동한 CMDB입니다.

## 순서를 이렇게 잡은 이유

| 순서를 바꿨다면 | 생겼을 문제 |
|---|---|
| 표준 절차 없이 Playbook부터 | 담당자마다 다른 조치가 그대로 코드가 됨 |
| Playbook 없이 웹 콘솔부터 | 화면은 생겨도 실제 조치는 여전히 사람이 서버에서 함 |
| 접근 통제 없이 콘솔만 | 직접 접속이 남아 보안 위험이 그대로 |

절차가 있어야 Playbook으로 옮길 수 있었고, Playbook이 있어야 웹 콘솔로 열 수 있었습니다.

## 그 밖에 정한 것

| 판단 | 대안 | 고른 이유 |
|---|---|---|
| 장애 유형 단위로 Playbook 작성 | 서버나 명령어 단위 스크립트 | 2019년에 정리한 유형이 이미 있었고, 엔지니어가 장애를 보고 고르는 단위와 같습니다. |
| SSO + proxy로 접근을 한 곳에 | 서버별 계정과 접근 통제 | 서버 6만 대+의 접근을 서버마다 관리하는 것보다 입구 하나를 통제하는 쪽이 현실적이었습니다. |
| 작업 대상은 Dynamic Inventory로 | 고정 inventory 파일 | 서버가 계속 입고되고 바뀌는 환경이라, CMDB를 원본으로 실시간으로 읽어야 대상이 틀리지 않습니다. |
| 처리 데이터를 Elasticsearch에 축적 | 처리 결과만 남김 | 유형별 장애 추세를 봐야 늘어나는 유형을 먼저 손볼 수 있습니다. |

## 결과

- 서버 직접 접속이 거의 없어졌습니다.
- 정형화된 장애는 Playbook 실행 한 번으로 수십 초 안에 처리합니다.
- 경험이 적은 엔지니어도 같은 절차로 처리할 수 있게 됐습니다.

## GPU 클러스터에서는

노드 상태 점검, 이상 노드 drain, 유형별 조치로 이어지는 GPU 클러스터 운영 흐름도 같은 형태입니다. 장애 유형을 먼저 정하고, 조치를 코드로 옮기고, 실행 창구를 하나로 모으는 순서는 그대로 쓸 수 있다고 봅니다.
