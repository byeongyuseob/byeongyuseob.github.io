## 요약

2021년 12월, 장애 관리 웹 프로젝트를 PM으로 시작했습니다. 2019년에 장애 대응 표준 절차는 만들어 두었지만, 실제 조치는 여전히 사람이 서버에 직접 접속해서 했습니다. 시작하면서 문제를 접근, 대상, 조치, 관찰 네 가지로 나누고 각각의 목표를 정했습니다.

## 당시 상황

- 서버 6만 대+에서 하드웨어·OS 장애가 하루 30~40건 발생했습니다.
- 장애가 늘면서 대응 인력과 서버 접근 횟수가 함께 늘었습니다.
- 여러 사람이 서버에 직접 접속하다 보니 보안 위험이 있었습니다.
- 경험이 적은 엔지니어는 같은 장애도 처리가 늦었습니다.

## 목표

| 나눈 문제 | 목표 | 방법 |
|---|---|---|
| 접근 | 서버 직접 접속을 줄이고 인증을 한 곳으로 모으기 | 중앙 인증(SSO)과 proxy 연동 |
| 대상 | 작업 대상 서버 정보를 사람이 모으지 않기 | Ansible Dynamic Inventory |
| 조치 | 누가 맡아도 같은 조치가 실행되게 하기 | 장애 유형 분류와 유형별 Playbook |
| 관찰 | 장애가 어디서 늘고 있는지 보기 | 웹 인터페이스와 장애 데이터 시각화 |

## 시작 전에 확인한 것

- 장애 유형: 2019년 표준 절차를 만들 때 정리한 유형 분류를 그대로 Playbook의 단위로 쓰기로 했습니다.
- 서버 정보: 2017년 수집 자동화 때 연동한 CMDB를 Dynamic Inventory의 원본으로 쓰기로 했습니다.

앞선 두 프로젝트에서 만든 것을 기반으로 삼았기 때문에, 이번 프로젝트는 접근 통제와 실행 창구를 만드는 데 집중할 수 있었습니다. 결과는 2022년 10월에 [따로 정리](/posts/incident-playbook-console/)했습니다.
