프로젝트 소개

실제 농장 피해 경험에서 출발한 서비스입니다

이 프로젝트는 2025년 아버지의 포도 농장에서 탄저병 피해를 겪은 경험에서 시작했습니다. 같은 피해를 조금만 더 일찍 알 수 있었다면 줄일 수 있었겠다는 문제의식이 출발점입니다.

병해조기경보는 단순한 데모가 아니라, 실제 운영을 염두에 둔 서비스로 설계하고 있습니다. 예측의 신뢰성, 근거 기반 설명, 운영 가능성을 처음부터 함께 고려하는 것이 목표입니다.

핵심 원칙

검증 가능한 판단 구조를 먼저 세웁니다

병해조기경보는 LLM 중심 서비스가 아니라, 예측과 설명의 역할을 분리한 구조를 지향합니다.

규칙 엔진이 먼저 판단합니다

병해 위험도는 규칙 기반 로직과 Random Forest를 중심으로 계산합니다. 판단 과정이 설명 가능하고 검증 가능해야 한다는 기준을 가장 먼저 둡니다.

LLM은 설명을 돕는 역할에만 사용합니다

LLM이 병해를 판단하지는 않습니다. 고령 농가가 이해하기 쉬운 설명, 체크리스트, 쉬운 표현 변환처럼 안내를 돕는 용도로만 사용합니다.

공식 문서를 근거로 설명합니다

농진청과 NCPMS 같은 공신력 있는 자료를 RAG로 연결해 답변의 근거를 분명히 하려고 합니다. 환각을 줄이고, 농가가 믿고 참고할 수 있는 설명을 만드는 것이 목적입니다.

AWS 기반 구축 계획

AWS 위에서 실제 운영 가능한 구조를 검증하려고 합니다

플랫폼

  • AWS 서울 리전 EKS를 기준으로 구성합니다
  • Terraform과 Helm으로 재현 가능한 배포 구조를 만듭니다
  • ArgoCD로 GitOps 운영 흐름을 준비합니다

애플리케이션과 추론

  • FastAPI로 핵심 API를 구성합니다
  • KServe와 vLLM으로 LLM 서빙을 계획합니다
  • Redis, PostgreSQL, ChromaDB로 실행 계층을 뒷받침합니다

운영

  • Prometheus, Grafana, Loki로 관측성을 확보합니다
  • Karpenter와 HPA로 오토스케일링을 적용합니다
  • Spot 우선 전략으로 비용 최적화를 추진합니다

추진 계획

  4. Phase 3: 관측성과 오토스케일링 구성
  5. Phase 4: GitOps, CI/CD, 안정화 작업

AWS Activate가 필요한 이유

AWS 크레딧은 EKS 검증, GPU 추론 실험, 관측성 구성, 오토스케일링 테스트를 실제 환경에 가깝게 검증하는 데 직접 필요합니다. 단순한 시연용 페이지가 아니라 운영 가능한 구조를 초기에 확인하려는 목적입니다.

이 프로젝트는 농업 AI도 충분히 신뢰 가능하고 운영 가능하게 설계될 수 있다는 점을 보여주기 위한 시도입니다. 예측 로직, 공식 문서 기반 설명, 클라우드 운영 구조를 함께 설계해 실제 서비스로 이어질 수 있는 기반을 만들고자 합니다.
